项目 01：大模型推理部署与测试交付

一次从模型启动、接口验证、性能采样到测试报告的本机工程实践。

本项目由 Codex 协助实现和测试；下面的结果是在 RTX 3090 上使用本地 Qwen2.5-1.5B 得到的，属于单机实验，不是昇腾或客户生产结果。

1. 项目解决什么问题

假设接到任务：“把模型部署到服务器，验证接口，然后比较不同并发下的延迟和吞吐。”工程交付不只是模型回复了一句话，还要记录环境、测试条件、原始数据、失败和结论边界。

记录环境与模型→启动本机服务→功能与异常测试→分组压测→核对数据并交付

2. 本次实际做了什么

  • 本地模型 Qwen2.5-1.5B-Instruct；单张 RTX 3090、FP16、最大上下文 1024、eager 模式。
  • 现有 vLLM 包元数据为 0.6.3，但模块版本字符串为 dev；CUDA 环境为 PyTorch 2.4.0+cu121。
  • 服务只监听 127.0.0.1:18101；健康、模型列表、普通生成、流式生成及两个异常用例通过。
  • 客户端压测采用 6 条固定短中文问题，每组 24 请求；并发 1、2、4 各复测 3 次，共 216 个正式请求。
  • 测试结束后关闭服务。参数、模型摘要、原始数据和项目文件详见 项目 README。

这是一套小规模本机验证，不代表模型回答正确率、长期稳定性、线上 SLA 或 NPU 的实际表现。单独提问 KV Cache 时，模型将其错误描述为缓存参数和输入以减少加载时间；这一条人工核查说明“接口可用”不等于“回答正确”，也不构成系统性质量评估。

3. 请求如何经过系统

测试客户端发请求→vLLM 接收与调度→GPU 模型生成→SSE 流式返回→保存时间、usage 和结果

客户端限制最大并发，当前请求结束后再发下一个，因此这是闭环并发测试。每次测试使用相同的问题集合和输出上限；单次请求时间不含客户端信号量外排队，整组吞吐以整组墙钟时间为分母。

4. 四个指标怎么理解

指标本项目如何测说明
TTFT请求开始 → 收到第一个非空文本块是用户可见首文本延迟的近似值；块可能包含多个 token。
E2E请求开始 → 收到 [DONE]包括流结束信号，不含客户端等待信号量时间。
TPOT(E2E − TTFT) / (输出 token 数 − 1)token 数取自服务端 usage；这是客户端估算，不是逐 token 间隔。
输出吞吐所有成功请求的输出 token 总数 / 整组耗时是整个服务的吞吐，不是一个请求的输出速度。

详细定义及 P95、显存采样的局限参见 测试方案。

5. 实际复测：并发变化会怎样

每组 24 请求，重复 3 次；下表是每轮平均值的三轮平均。TTFT 和 TPOT 是客户端近似，结果由脚本与原始数据计算得到。

并发成功/总数平均 TTFT / ms平均 TPOT / ms输出吞吐 / token·s⁻¹
172/7214.8211.3587.54
272/7216.1111.58171.40
472/7226.2011.73332.70

在本次短输入、短输出条件下，提高并发时总输出吞吐提高，首个可见文本的等待时间也增加。它说明吞吐与单请求延迟是不同指标；它本身不能证明具体性能瓶颈，也不能预测更高并发的结果。

每轮输入平均约 45 个 token，输出平均 48 个 token；每轮只有 24 条请求，P95 不足以代表线上长尾。完整逐轮结果和原始文件见 测试报告、results 目录。

6. 真实故障：健康检查通过，生成返回 500

服务启动后 /health 返回 200，但第一次聊天生成失败。日志显示请求进入 outlines 解码后端时，pyairports 模块导入失败；系统有包元数据，但不能据此断言环境为什么出现这种状态。

处理时使用本机已有的 lm-format-enforcer 后端，等待服务就绪后重新验证，最终 6 项真实 API 测试和 3 项脚本单元测试通过。这说明“健康接口成功”和“核心功能可用”是两种检查。

另一次排查发现该 vLLM 构建会提前绑定全部地址，因此项目启动脚本对指定端口做了回环绑定处理，重启后用 ss 确认。详情见 问题排查记录。

7. 跟着完成一次技术交付

  1. 先检查 GPU 和端口，解释模型、精度、版本和请求参数。
  2. 启动服务并确认监听地址；访问健康接口和模型列表。
  3. 运行 6 项 API 测试，读失败信息，不把 200 健康检查当成全部成功。
  4. 从 6 请求冒烟开始，逐步测试并发 1、2、4，查看逐请求记录。
  5. 以“条件 → 数据 → 观察 → 限制 → 后续验证”的结构写报告，再关闭服务。

具体命令和每一步的问题在 跟着做：一次完整测试交付。

8. 核心文件

  • serve_loopback.py：启动旧版 vLLM 并将指定端口绑定本地。
  • benchmark.py：闭环并发、流式采集、失败处理、显存采样与结果保存。
  • test_api.py / test_benchmark.py：实际接口与压测脚本的基础测试。
  • capture_environment.py：记录设备、依赖版本和模型 SHA256。
  • build_report.py：从正式复测 summary 生成报告。
