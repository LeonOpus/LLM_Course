一、先用一句话理解这个项目

用户上传资料 → 系统解析资料 → 切成小段 → 生成向量并写入 Elasticsearch → 用户提问 → 混合检索和重排 → 大模型根据检索结果回答，并把来源返回给用户。

所以 Lesson 5 的重点不只是“向量相似度”，而是完整链路：文件怎么进来、数据怎么存、用户能不能看别人的资料、服务怎么流式返回、外部服务挂了怎么办。

三、代码目录应该怎么读

目录 / 文件大白话作用面试时怎么说
backend/app/app_main.py创建 FastAPI 应用，挂载路由和跨域配置。应用入口，不是业务逻辑全部塞在一个文件里。
router/把登录、会话、历史、上传、聊天等 HTTP 接口分开。路由层负责协议和参数，业务下沉到 service。
service/core/file_parse.py串起文档解析、切块、向量化和写入 ES。这是离线 ingestion（入库）链路。
service/core/deepdoc/解析 PDF、DOCX、Excel、HTML、Markdown 等资料。复杂 PDF 需要 OCR、版面识别、表格识别，不能只靠简单字符串切分。
service/core/rag/app/naive.py按文件类型解析，并把内容合并成 chunk。chunk 是检索的基本单位，太大或太小都会影响召回和成本。
service/core/rag/nlp/中文分词、关键词、Embedding、Rerank 等。关键词检索和向量检索互补，重排负责最后精排。
service/core/rag/utils/es_conn.py管理 Elasticsearch 连接、索引和批量写入。生产环境要考虑连接池、超时、重试、批量大小和索引 mapping。
models/、database/、alembic/数据库模型、操作函数和迁移脚本。业务元数据与检索正文分离存储。
docker-compose.yml描述 API、ES、PostgreSQL、Redis 等服务如何一起启动。这是部署拓扑，不是 Python 代码本身。

四、离线入库和在线问答是两条链路

1. 上传资料：慢，但只需要做一次

  1. 前端上传文件，后端检查用户、文件类型和大小。
  2. 解析文本、表格、图片或 PDF 页面。
  3. 清洗乱码、保留标题和页码等 metadata。
  4. 切成 chunk，给每个 chunk 一个稳定的 doc_id、chunk_id、文件名和时间。
  5. 批量调用 Embedding 模型，写入 ES。

2. 用户提问：快，且会被调用很多次

  1. 把问题改写、分词或提取关键词。
  2. 同时做 BM25 全文检索和向量检索。
  3. 合并候选结果，必要时用 Reranker 精排。
  4. 过滤用户无权访问的文档。
  5. 把 Top-K 片段、引用信息和问题放进 Prompt。
  6. 调用 LLM，以 SSE/流式方式把答案逐步返回前端。
关键面试点：Embedding 发生在“入库时”和“问题检索时”；LLM 不是直接读完整数据库，而是只看到本次检索选出来的上下文。RAG 的质量首先受数据解析、切块和检索影响，然后才是 Prompt。

五、为什么用 Elasticsearch，不直接用一个向量库

方式擅长什么短板
BM25 / 倒排索引专有名词、编号、股票代码、精确关键词。同义表达、语义相近但词不同的内容不容易找到。
向量检索“意思相近”的问题和资料，即使字面不一样也能召回。可能把语义相近但事实不相关的内容召回。
混合检索把关键词的精确性和向量的语义能力结合。需要调权重、去重、统一分数和评测。
Rerank对少量候选重新判断“问题和片段是否真的匹配”。增加一次模型调用和延迟，不能对全库运行。

一个常见生产策略是：先召回几十条候选，再重排到 5～10 条，最后把少量高质量片段给 LLM。不要一上来把几十条甚至整本 PDF 塞给模型。

六、chunk 为什么这么重要

chunk 可以理解成“让检索系统拿来比较的一小段资料”。

切得太小切得太大合理做法
上下文不完整，问题和答案被切开；召回后模型看不懂。每个结果带很多无关内容；Token、延迟和显存成本上升。按标题、段落、页、表格语义切分，保留必要 overlap，并保存来源 metadata。

本项目的 naive.py 会针对 DOCX、PDF、Excel、TXT 等不同格式采用不同解析器，再做合并和 token 数控制。它不是“每 N 个字符硬切”这么简单。

八、面试时可以这样讲这个项目

问：这个项目和普通 RAG Demo 的区别是什么？
答：普通 Demo 往往是“加载文件、向量化、相似度搜索、拼 Prompt”。这个项目增加了登录和会话、文档上传、异步/批量入库、ES 索引、数据库元数据、Redis、流式输出、来源引用和前端交互，设计覆盖从数据进入系统到答案返回的链路；本次真实模型问答尚未验证成功。
问：为什么要混合 BM25 和向量检索？
答：BM25 对专有名词、编号和精确词很强，向量检索对同义表达和语义相似很强。两者召回结果合并后再做去重和重排，通常比只用一种检索更稳，但最终必须用离线评测集调权重，而不是凭感觉。
问：如何防止 RAG 把答案编出来？
答：先提高召回内容的相关性和完整性；Prompt 要求只能依据给定资料回答，不能找到证据时明确说不知道；答案附带文档名、页码或 chunk 来源；再用命中率、引用准确率、答案忠实度做评测。RAG 不能保证零幻觉，只能降低无依据生成。
问：权限应该放在哪一层？
答：不能只在前端隐藏按钮。后端要在上传、查询、删除、历史消息和检索结果返回前都校验 user/session/knowledge base 的归属。尤其要在检索过滤阶段限制文档范围，否则模型可能看到用户无权访问的 chunk。
问：怎么定位“召回率低”？
答：先把问题、标准答案、应命中的文档 chunk 做成评测集；分别测解析是否丢字、chunk 是否切坏、Embedding 召回 Top-K、BM25 召回 Top-K、混合后排名和 Rerank 后排名。不要直接把所有问题归因给 LLM。
问：如何优化线上延迟？
答：离线阶段批量解析和批量向量化；在线阶段缓存热门问题和 Embedding，限制召回候选数，Rerank 只处理小集合，LLM 使用流式输出；同时记录解析耗时、检索耗时、Rerank 耗时、首 token 时间和总生成时间。

九、你现在最应该记住的 10 个词

词一句话记忆
Ingestion把用户资料处理并写入检索系统的离线/准实时流水线。
Chunk检索系统拿来比较和返回的最小知识片段。
Embedding把文字变成可以计算语义距离的向量。
BM25基于关键词和词频的经典全文检索算法。
Hybrid Search关键词检索和向量检索一起召回。
Rerank对初筛结果再次判断问题和片段的真实相关性。
Metadata文件名、页码、用户、时间、权限等“正文以外但非常关键的信息”。
Grounding让回答有检索证据，而不是只靠模型参数记忆。
SSE服务器持续推送文本，让用户边生成边看到答案。
Observability记录日志、指标和链路耗时，知道系统到底慢在哪里、错在哪里。

十、后续学习顺序

  1. 先能画出“上传入库”和“提问检索”两条链路，并指出每个代码文件的位置。
  2. 自己做一份 20～50 条问答评测集，记录 Recall@K、MRR、引用准确率和端到端延迟。
  3. 把混合检索中的 BM25、向量召回、融合、Rerank 分别开关，比较结果而不是只看最终答案。
  4. 补上权限过滤、重复文件、文档更新、索引删除、失败重试和日志追踪。
  5. 最后再研究部署、并发、缓存、批处理和模型服务优化。
