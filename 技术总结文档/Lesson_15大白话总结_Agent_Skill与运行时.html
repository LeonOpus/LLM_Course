Lesson 15：Agent Skill 与运行时

把经验封装成可复用的技能，再用 Agent 循环、工具和权限系统把任务做完。

一句话：Skill 是给 Agent 的任务说明书；运行时负责把用户请求、技能说明、模型和工具连接起来，并控制执行与记录状态。

2. 它解决什么问题？

假设 Agent 要做数据分析：只告诉模型“帮我分析”可能每次步骤不一致。可以把选工具、清理数据、画图和交付文件的约定写入 Skill；下次遇到相似任务，Agent 先读取这份说明，再结合当前数据执行。

4. Skill 是什么？

Skill 可以理解为一个能力包，常见组成是：名称和用途描述、执行步骤、必要的参考资料，以及可选脚本或模板。它是给模型和运行时看的工作说明，本身不等于一个自动执行的函数。

skills/data-analysis/
└── SKILL.md      # 示例中的名称、描述和操作说明

系统提示先提供技能名称和描述
  → 模型认为任务匹配
  → 请求 read_file 读取 SKILL.md
  → 使用其中的步骤与工具处理任务

第一周项目的 SkillManager 在扫描时会将文件内容读入内存，但构造给模型的系统提示主要列出元数据和文件路径；完整指令由模型通过工具按需读取。这种“先看到简介，再获取细节”的做法有助于避免把全部长说明都塞进每次模型上下文，也不保证模型一定会正确选择或遵循。

第二周项目的加载器采用另一种约定：扫描用户和项目级技能目录中的直接 .md 文件，SkillTool 按名字返回提示文本。它和第一周示例的 技能目录/SKILL.md 结构不同，不能直接假设两者完全兼容。

5. Skill、工具、MCP、RAG 怎么区分？

概念负责什么例子
Skill描述何时采用哪些步骤、规范或参考资料。“数据分析时先检查缺失值，画图后说明结论”。
工具提供程序可以执行的具体动作。读取文件、执行 Python、搜索。
MCP一种连接工具和资源服务的协议；具体行为取决于客户端与服务端实现。通过 MCP 客户端发现和调用某个服务提供的工具。
RAG从外部知识中检索与问题相关的材料，供当前回答参考。根据用户问题检索企业文档。

一次任务可以同时用到它们：按 Skill 的分析规范，调用工具读取数据，必要时通过 MCP 获取资料，再用 RAG 补充知识。Skill 不能替代权限控制，检索结果也不是天然可信的指令。

6. 一次请求怎么运行？

  1. 启动时扫描技能，读取 frontmatter 中的名称和描述，并向模型提供可用工具的输入格式。
  2. 用户提交请求；模型根据上下文输出文字，或产生 tool_use：工具名、参数和调用 ID。
  3. 程序按名称分发工具；例如 read_file 读取 SKILL.md。把输出包装为关联调用 ID 的 tool_result。
  4. 把完整的 assistant 工具请求与工具结果加入消息历史，再调用模型。直到返回结束或达到最大轮数。
  5. Web 版本将轮次、工具调用、结果等通过 SSE 推到页面，并保存对话日志。真实执行失败时要结束流并展示错误。
用户请求 → 模型 + Skill 摘要 + 工具定义
        → tool_use（名称、参数、ID）→ 程序执行
        → tool_result（关联 ID）→ 模型继续 → 完成

这条链路与 Lesson 13/14 的工具调用相通；本课新增的重点是把操作经验组织成可复用的 Skill，以及将运行时设计成可管理的工程组件。

7. 编程 Agent 的运行时

QueryEngine 管理模型、工具和一次对话；query_loop 负责模型与工具之间的多轮状态流。项目还实现了工具执行器、权限检查、上下文压缩、会话保存和消息通信等模块。

  • 流式工具执行：代码在收到完整工具调用信息后可以安排工具执行，减少等待；有依赖或有写入冲突的操作不能盲目并行。
  • 权限门控：课程实现中只读工具可自动允许，其他工具根据模式和规则决定；非交互场景无法询问时会拒绝需要确认的操作。
  • 上下文压缩：历史过长时用摘要替换部分消息，降低上下文占用；代价是细节可能丢失，需要保留关键约束与可追溯记录。
  • 会话和多 Agent：课程代码有会话存取、任务状态与消息通信模块；本次仅通过项目离线测试验证相应模拟行为，没有真实模型驱动的团队协作验证。

第一周的执行器直接在本机运行 Python 和 shell，简单的危险词过滤并不是安全沙箱，且网页没有鉴权。不要将它直接暴露到公网；真实部署需要隔离环境、访问控制、权限审批、资源限制和审计。

8. SFT 与 RL 数据怎么看？

SFT 数据中的 messages 保存 system、user、assistant 和 tool 等多轮轨迹，tools 保存可用工具定义。学习目标通常是根据历史预测合适的 assistant 输出；真正训练时还需要验证 chat template、标签 mask 和截断策略。

RL 文件中主要包含 prompt、reward_model、extra_info 等字段。数据文件提供训练输入和奖励相关信息，但不能仅凭文件名或 manifest 就认定 GRPO、奖励函数或训练效果已经跑通。模型、执行环境、奖励实现和评估配置仍需单独准备。

第一条 SFT 在本机分词器下约 5,969 tokens，若简单截断到 2,048，可能丢掉工具轨迹或监督目标。训练前应统计全量长度分布、检查每条样本截断后的有效标签，并用独立评估集检查工具选择、参数、执行结果和最终答案。

11. 面试表达

30 秒

我学习了一个本地 Skill Agent：启动时提供技能简介，模型需要时通过文件工具读取详细步骤，再在 Agent 循环中调用工具并处理结果。我用模拟模型验证了技能加载、工具结果回传和网页事件流，还跑通了另一个 Python 编程 Agent 的 498 个离线单元测试；真实云模型和训练效果没有验证。

2 分钟

Skill 是可以复用的任务规范，可以包含触发描述、详细步骤和参考文件。运行时把可用技能概要和工具定义提供给模型；模型选择后请求工具读取具体说明，再用工具处理用户任务。每次工具请求都要由程序执行并把结果关联到原调用，然后继续模型循环。相比把所有说明放进系统提示，按需加载有助于控制上下文，但依赖模型正确选择，且不能替代权限控制。

工程上我关注最大迭代次数、工具权限、对话记录、错误结束以及上下文压缩。课程还提供一个编程 Agent 实现，使用权限门控和流式事件；我完成了离线测试，真实服务和安全隔离仍需验证。训练数据方面，工具轨迹可以用于 SFT 或 RL，但要检查格式、长度、标签与独立评测集。

常见追问

Skill 和工具有什么区别？Skill 描述做事方法，工具提供具体动作；一个 Skill 可以组合多个工具。

为什么要按需加载？减少每轮无关说明进入上下文的开销，但需要评估技能选择是否正确、遗漏时如何发现。

如何评估 Skill？在独立任务集对比有无 Skill 的成功率、步骤与工具参数正确率、执行成本和失败恢复，检查是否只是在测试集上过拟合。

模型输出的命令为什么不能直接信任？模型、网页和文件内容都有可能产生不合适的操作；要用程序侧的权限、隔离和审计来约束。
