1. 一句话：这一课解决什么问题？

学习训练太慢或模型、梯度与优化器状态放不进一张卡时，怎样把计算或状态分配到多个进程和设备，并理解随之产生的通信成本。

大白话：接上 Lesson 7–10

前几课我们已经见过模型前向、loss、反向传播和参数更新。当模型和数据变大，一张 GPU 可能太慢，也可能显存不够。这一课不改变“用数据计算 loss、再更新参数”的基本目标，而是研究怎么让多个设备分工。

分工有不同方向：数据并行让多个副本各处理不同数据；模型并行把模型计算拆开；ZeRO把部分训练状态分片。分得越细，可能越省单卡显存，但通信、调度和故障处理通常也更复杂。

当前机器只有一张 RTX 3090。本次使用两个 CPU 进程验证 DDP 梯度同步，并用单 GPU 跑课程 Trainer；没有实际验证双 GPU、多机、DeepSpeed ZeRO 或训练加速比。

2. DDP：不同数据，怎样更新成同一个模型？

同一批数据拆成两份
进程 0：模型副本 + 数据 A → 本地 loss → 本地梯度 ┐
进程 1：模型副本 + 数据 B → 本地 loss → 本地梯度 ├→ 梯度同步 → 各自执行相同更新
                                                   ┘

DDP（DistributedDataParallel）通常采用一进程一 GPU；每个进程处理自己那份数据。反向传播过程中，DDP 会把梯度分桶并触发集合通信，常见情况下对各进程梯度做平均。更新后，各副本可以保持一致；不是只在 GPU 0 更新完再把参数广播给其他 GPU。

这次真实实验的具体例子

在 ddp_cpu_demo.py 中，8 条样本分给两个 CPU 进程：

rank 0 → 样本索引 [0, 2, 4, 6]
rank 1 → 样本索引 [1, 3, 5, 7]
每个进程：相同模型 → 本地 MSE loss → backward → SGD 更新

实测两个进程更新后的模型参数一致；与单进程使用全部 8 条样本完成一次更新相比，最大参数差为 1.49×10⁻⁸。两边 loss 不同很正常，因为看到的数据不同。

这里两边 batch 大小相同、loss 均按相同方式取平均、初始权重相同、只进行一次 SGD 更新，因此结果可比较。遇到不同 batch 大小、随机层、不同优化器或梯度累积方式时，不能无条件声称结果完全相同。

rank、world size 和通信

  • world size：参与当前分布式作业的进程总数，本实验是 2。
  • rank：进程在整个作业中的编号，本实验为 0 和 1。
  • local rank：进程在当前机器内的编号，常用于多 GPU 场景绑定本机设备。
  • All-Reduce：让多个进程共同聚合数据并使参与者获得结果；DDP 梯度同步通常以归约为基础。Gloo 与 NCCL 是不同通信后端，本次使用 CPU 的 Gloo，没有验证 NCCL。

3. 显存里有什么？ZeRO 分什么？

训练显存不仅是模型权重，还可能包括梯度、Adam 的一阶/二阶动量等优化器状态、激活值、临时缓冲和通信缓冲。具体字节数取决于参数精度、优化器、是否保留 FP32 主权重、实现方式和序列长度；不能只用参数量直接推断实际显存。

方式主要分片内容仍要考虑
普通 DDP每个数据并行进程通常保留完整参数副本，梯度在训练中同步。提升数据吞吐的同时，单卡通常仍需容纳完整模型和相关状态。
ZeRO-1分片优化器状态。参数及梯度仍有各自的存储与通信需求。
ZeRO-2分片优化器状态和梯度。参数通常仍以副本形式存在，实际显存还包括激活和临时缓冲。
ZeRO-3进一步分片模型参数。计算时需要按需获取参数，通信和实现复杂度会提高。

FSDP 也是一种模型状态分片训练方式；它与 ZeRO 思路有相似之处，但具体策略、实现与配置不能直接视作完全等同。本机没有实测这些方案的显存或性能。

混合精度和梯度累积

FP16/BF16 可用于部分运算以降低资源消耗或提升吞吐；FP16 常配合梯度缩放避免小梯度下溢，BF16 数值范围较大，是否使用缩放取决于实现。梯度累积让多个小 batch 共同贡献一次参数更新。

常见有效 batch = 每设备 micro-batch × 梯度累积步数 × 数据并行进程数

例如每卡 4 条、累积 8 次、2 个数据并行进程，常见有效 batch 为 64。遇到不完整 batch、不同加权或特殊并行维度时，需要以实际训练实现为准。

4. 数据并行之外：模型怎么拆？

方式拆分对象收益和代价
数据并行 DP / DDP数据 batch；每个进程使用模型副本。可扩大数据处理规模；需要同步梯度，通常不能解决单卡放不下完整模型的问题。
张量并行 TP层内部的大矩阵或计算切分到多个设备。单卡承担部分权重和计算；层内需要频繁通信，对互联带宽敏感。
流水线并行 PP把不同层划分到不同设备，按阶段传递激活和梯度。可容纳更深的模型；需要处理流水线空泡和阶段负载不均。
序列并行在特定实现中按序列维度分担部分计算或激活。有助于长序列场景；具体切分范围和通信取决于实现，不同框架定义可能不同。
专家并行 EP将 MoE 的专家分布到多个设备，按路由分发 token。分担专家参数；需要 token 分发与聚合，还要处理专家负载不均。

真实大规模训练可能组合多种并行策略。通信拓扑、网络带宽、batch 大小和模型结构决定实际性能；增加设备不保证线性加速。

7. 常见问题：现象、原因和排查

现象可能原因与排查
启动时提示 GPU 数量不足检查 nvidia-smi、可见设备和进程数量；单卡不能真实模拟双卡 NCCL 训练，本次选择两个 CPU 进程验证同步逻辑。
进程等待或训练卡住检查各进程是否都进入相同的集合通信、rank/world size 配置是否一致，以及端口、网络和某个进程是否提前报错。
多卡却没有变快检查数据加载、micro-batch、通信时间、设备利用率和负载不均；DDP 的通信开销可能抵消部分计算收益，需实际测量。
显存仍不足区分参数/优化器状态、激活和临时缓冲；视瓶颈考虑较小 batch、梯度检查点、混合精度、状态分片或模型并行，不要只看权重大小。
结果和单卡有差异核对样本划分、loss 平均方式、随机数、梯度累积、有效 batch 和学习率；浮点归约顺序也可能造成微小数值差异。

保存与恢复还应核对是否包含优化器、调度器、随机数、数据位置及分片元信息；只有模型权重不等于能无损恢复训练过程。

8. 面试版回答

30 秒

分布式训练主要解决计算吞吐和单卡资源限制。数据并行让多个模型副本处理不同数据并同步梯度；ZeRO 进一步按阶段分片优化器状态、梯度和参数。我在单机用两个 CPU 进程实际验证了 DDP：不同样本分片后更新参数一致，并和单进程完整 batch 的结果做了对照；没有实测多 GPU 或 DeepSpeed。

2 分钟

训练显存包括权重、梯度、优化器状态、激活和临时缓冲。普通 DDP 通过多个进程处理不同数据，反向传播同步梯度，各副本执行更新；当状态冗余导致显存压力时，ZeRO-1、2、3 分别逐步分片优化器状态、梯度和参数。模型放不下或计算量更大时，也可以考虑张量、流水线和专家并行，但需要权衡通信和负载。

我基于课程 SimpleNet 写了一个双 CPU 进程 Gloo 验证，检查样本分片、同步后的参数一致性，并对照单进程全 batch，最大误差约 1.49×10⁻⁸；还用 3090 跑了 8 步单 GPU Trainer。因为机器只有一张 GPU，这些结果不能证明多 GPU 加速或 ZeRO 显存收益。

追问速答

  • DDP 是只让 rank 0 更新吗？通常每个进程在同步梯度后都对各自副本执行更新；rank 0 常额外负责日志或保存。
  • DDP 能让放不下一张卡的完整模型跑起来吗？普通 DDP 通常保留完整模型副本；这种情况需要考虑参数分片或模型并行等方法。
  • ZeRO-1/2/3 区别？分别逐步分片优化器状态、再加梯度、再加参数；实际显存还受到激活与通信缓冲影响。
  • 为什么多卡未必快？通信、数据加载、负载不均和较小 batch 都可能限制收益，应以吞吐、显存与通信时间实测。
  • 有效 batch 怎样计算？常见公式是每设备 micro-batch × 累积步数 × 数据并行进程数，但要核对不完整 batch 和框架细节。
  • 这次你真正验证了什么？两个 CPU 进程的 DDP 同步和单 GPU Trainer；未测多卡 NCCL、ZeRO 或多机。
