1. 一句话：这课解决什么问题？

学习如何降低模型存储和推理成本，并理解不同优化对显存、速度、质量和工程复杂度的影响。

前几课我们学习了模型结构、训练和分布式；部署时还会遇到“显存放不下、响应慢、并发低”的问题。量化主要改变数值表示；蒸馏通过训练让学生学习教师提供的知识或行为；Flash Attention 优化注意力计算的数据搬运；KV Cache 避免重复计算历史 token 的 K/V。

不要把“更省显存”等同于“一定更快”。计算内核、硬件、batch、上下文长度和服务方式都会改变结果。本机这次 INT8 就比 BF16 慢。

2. 量化：用更少的位表示数

大白话：把较精细的数值映射到较少的离散刻度，再在需要时近似还原。这样可以减少部分权重的存储量，但会引入量化误差，也可能带来量化/反量化及额外元数据的成本。

示意仿射量化：
q = clip(round(x / scale) + zero_point)
x近似 = scale × (q − zero_point)

x 是原始值，q 是量化后的离散数，scale 是缩放因子，zero_point 是零点，clip 表示限制在可表示范围。实际算法可能采用对称/非对称、逐通道/分组、不同编码及校准方式；NF4 不是简单的均匀 INT4。

方案要点边界
BF16 / FP1616 位浮点格式；BF16 和 FP16 的指数与精度分配不同。不是 4/8 位整数权重量化。
BitsAndBytes INT8部分线性层使用低比特权重与对应运算路径。其他模块、量化元数据和计算缓冲仍占空间；速度依赖实现和硬件。
NF4 / QLoRANF4 常用于 4-bit 权重表示；QLoRA 在量化基础模型上训练 LoRA 增量。本次只做 NF4 推理；蒸馏训练使用 BF16 + LoRA，不是本次 QLoRA 训练。
GPTQ、AWQ、GGUFGPTQ/AWQ 是量化方法或流程；GGUF 是模型文件格式生态，常承载多种量化表示。不是互相等价的“同一种算法”；本次没有运行这些格式或方案。

模型为本地 Qwen2.5-1.5B-Instruct，单张 RTX 3090，输入 39 token，batch 1；使用 Transformers + BitsAndBytes，贪心生成，强制生成 64 个新 token。每种配置先预热，再测 3 次，统计平均速度。

配置模型新增 GPU 已分配运行新增峰值平均 token/s
BF162.876 GiB2.892 GiB62.06
INT81.718 GiB1.752 GiB13.68
NF4 + 双重量化1.074 GiB1.102 GiB43.38

这里的显存是 PyTorch memory_allocated 相对加载前基线的增量，不等于 nvidia-smi 的整卡总占用，也不包含其他进程、所有驱动/运行时开销或长期服务碎片。token/s 从一次 generate 开始计时，包含该次输入处理和生成；不是单独测量的 decode 吞吐，也不是多并发压测。

本次数据说明：INT8、NF4 的模型分配显存更低，但当前单请求实现中两者都慢于 BF16。不能据此推广到其他模型、内核、硬件、并发或上下文长度。

测试脚本和结果：quantization_benchmark.py、quantization_benchmark_result.json。这是速度与内存实验，不是任务准确率测试；要评估精度，还需固定数据集和指标进行前后比较。

结合原始结果再看质量：本次计时用的问题涉及大模型的 KV Cache，但结果 JSON 中三种配置的回答都把它解释成类似数据库键值缓存的概念。这是该次生成的具体错误示例，说明生成成功和速度快不代表回答正确；仅凭一条输出也不能比较哪种量化的整体准确率更高。

5. Flash Attention：减少中间数据搬运

普通注意力概念上先计算 QKᵀ、softmax，再乘 V。长序列下中间注意力矩阵很大；Flash Attention 使用分块和在线 softmax 等方法，尽量减少 GPU 显存与片上存储之间的中间数据读写。它计算的是同一注意力目标的高效实现，但由于浮点计算顺序不同，结果不必逐位相同。

这次用 PyTorch SDPA 强制选择两个后端，在相同随机输入、FP16、因果注意力、[B,H,T,D]=[1,8,512,64] 下，各预热 10 次、测量 100 次：

后端单次平均耗时数值对比
数学后端约 0.273 ms作为本次对比基准。
Flash 后端约 0.0215 ms与数学后端最大绝对差约 0.000977，平均绝对差约 0.0000172。

这是单个注意力算子的计时，不是完整模型或线上服务加速比；还没有比较不同序列长度、batch、硬件或反向传播。源码 attention_benchmark.py，结果 attention_benchmark_result.json。

6. KV Cache 与 PagedAttention：接回 Lesson 2

KV Cache 保存历史 token 在各层 Attention 中计算出的 K/V。生成新 token 时，用新 Q 和历史 K/V 做注意力，减少重复计算；缓存本身会随历史长度、batch 和层数增加，占用显存。

近似 KV Cache 字节数 = 2 × 层数 × batch × 序列长度 × KV头数 × 每头维度 × 每元素字节数

系数 2 表示 K 和 V；实际实现还可能有对齐、分块、量化、并行切分和元数据等额外影响。GQA 的 KV 头数较少，可以降低对应缓存规模。

PagedAttention 在支持它的推理框架中以块管理 KV Cache，目的是改善动态分配、复用及碎片管理；它不是把 KV Cache 消除，也不保证任何负载都一定更快。本次没有运行 vLLM 或验证 PagedAttention 的吞吐。

9. 面试版回答

30 秒

我用本地 1.5B 模型对比了 BF16、BitsAndBytes INT8 和 NF4 的单请求推理：量化降低了模型分配显存，但本机 INT8 反而比 BF16 慢。我还比较了 PyTorch 数学和 Flash 注意力后端的单算子耗时与数值差异，并用课程现成回答数据跑通了 4 步 LoRA 学生训练；这些都是小规模验证，不代表完整服务压测或蒸馏效果。

2 分钟

推理优化需要先区分瓶颈。量化用低比特近似表示权重，可能降低显存，但实际速度取决于内核和负载；蒸馏用教师输出或分布训练学生；Flash Attention 通过分块和减少中间数据搬运优化注意力；KV Cache 缓存历史 K/V，减少 decode 重复计算，但会占显存。

在 3090 上，我用同一 1.5B 模型、39 token 输入和 64 token 输出测了 BF16、INT8、NF4，模型新增分配显存约 2.876、1.718、1.074 GiB，单请求速度约 62、14、43 token/s。测试只代表当前设置。蒸馏部分使用课程预存回答做了 4 步训练，教师来源和训练效果未独立验证；Flash Attention 只做了单算子测试。

面试追问

  • 量化为什么有时反而慢？低比特路径可能有转换开销，且内核、硬件和负载影响性能；本次没有 profiler 数据，不断言具体原因。
  • LoRA 和 QLoRA 区别？LoRA 训练低秩增量；QLoRA 通常在低比特量化基础模型上训练 LoRA。本次 NF4 推理和 BF16 LoRA 训练是两个独立实验。
  • Flash Attention 是近似注意力吗？常见 Flash Attention 实现目标是计算标准注意力，浮点舍入可导致微小差异；本次未做逐位一致或训练收敛验证。
  • KV Cache 是什么？各层历史 token 的 K/V 中间结果，不是问题和答案的标签；减少重复计算但增加显存占用。
  • 蒸馏成功怎么判断？在独立测试集上比较学生训练前后、质量与目标指标，并评估成本；仅跑出 loss 不够。
