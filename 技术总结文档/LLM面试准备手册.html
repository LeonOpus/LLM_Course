LLM 面试追问大白话准备手册

面向：大模型推理工程师、AI Infra、vLLM/vLLM-Ascend、RAG 后端岗位

先说结论：你不需要把整个大模型领域都背下来。面试官真正想确认的是：你是否知道系统怎么工作、指标怎么测、问题怎么定位，以及简历上的结果是不是你真的参与过。
本手册内容：

一张总图 · vLLM 调度 · PagedAttention · Continuous Batching · KV Cache 显存 · TTFT / TPOT · Prefill / Decode · Tensor Parallel · vLLM-Ascend · 大模型压测 · RAG 评测 · Beam Search 排障

一、先建立一张总图

把一次大模型请求想象成一家餐厅：

大模型组件大白话面试时要讲清楚
Prefill厨师先把用户整段需求读完，准备好上下文。输入很长时，主要影响首字出来的速度。
Decode厨师一个字一个字地把答案写出来。生成很长时，主要影响每个字的生成速度。
KV Cache把已经读过的内容做成临时笔记，不必每次重读。省计算，但会占显存，并且随上下文长度增长。
Continuous Batching新客不断加入，做完的客人随时离开，不必等整桌人一起结束。提高 GPU 利用率和整体吞吐。
PagedAttention把临时笔记切成小页，需要多少拿多少。减少 KV Cache 的内存浪费和碎片。
Tensor Parallel一份大菜由多名厨师分工完成。把模型权重或计算切到多张卡，需要通信同步。
面试总回答：我会从请求生命周期、显存管理、批处理调度和多卡通信四个角度分析推理系统：先区分 Prefill 与 Decode，再看 KV Cache 如何分配，之后看请求如何动态组 batch，最后判断多卡通信和算子执行是否成为瓶颈。

二、vLLM 的调度到底在调度什么

vLLM 的调度器主要决定：哪些请求现在执行、每个请求这一步生成多少 token、GPU 显存还够不够放 KV Cache。

请求通常会经历：

  1. 等待：请求进入队列。
  2. Prefill：一次处理输入 Prompt，建立初始 KV Cache。
  3. Decode：每一轮生成一个或多个新 token，并追加 KV Cache。
  4. 完成：遇到 EOS、达到最大长度或被取消，释放资源。
大白话：调度器像网约车派单系统。它不能只看“来了多少乘客”，还要看每个乘客的行李有多大——这里的行李就是 KV Cache。显存不够时，不能盲目接新请求。
可直接回答：vLLM 调度器会根据等待请求、运行中请求、最大序列长度和可用 KV Cache block 安排每一轮执行。它的目标不是简单地一次处理一批固定请求，而是在请求不断到来和结束的情况下动态分配计算与显存资源。

追问方向：调度策略会受到最大 batch token 数、最大并发数、GPU 显存利用率、KV Cache block 数量以及请求输入输出长度的影响。具体参数要以实际启动命令和 vLLM 版本为准。

三、PagedAttention 是什么

普通做法可能给每条请求预留一大片连续的 KV Cache 空间，但用户的真实输出长度通常未知：

  • 预留太多：浪费显存。
  • 预留太少：生成到后面可能不够。
  • 不同请求长度不同：容易出现显存碎片。

PagedAttention 把 KV Cache 切成固定大小的小块，类似操作系统把内存切成页面：

逻辑上：请求 A 的 KV Cache = [A0][A1][A2][A3]
物理上：这些 block 不一定连续，可以放在显存不同位置

请求结束后：释放它占用的 block，供其他请求复用
可直接回答：PagedAttention 的核心不是改变 Attention 数学公式，而是改变 KV Cache 的存储和访问方式。它通过 block 化管理，让 KV Cache 不需要为每个请求预留大段连续空间，从而降低碎片和预分配浪费，提高并发能力。
不要说错：PagedAttention 不是“把模型参数分页”，它主要解决的是推理过程中 KV Cache 的显存管理问题。

四、Continuous Batching 为什么有用

传统静态 batching 像等一整车人到齐后再发车：最慢的请求不结束，其他请求也可能被拖住。

Continuous Batching 是动态批处理：

时刻 T1：请求 A、B 在 Decode
时刻 T2：A 完成，释放资源；请求 C 加入
时刻 T3：B、C、D 一起执行下一轮 Decode

它提高的是整体 GPU 利用率和吞吐量，不一定让单个请求的延迟变低。并发太高时，单请求延迟仍可能上升。

面试回答：Continuous Batching 允许请求在不同时间进入和退出 batch。它把正在生成的请求和新到达的请求动态组合，减少 GPU 空转，特别适合在线推理场景。但它需要调度器同时考虑请求状态、token 预算和 KV Cache 显存。

五、KV Cache 如何占显存

每个 Transformer 层都会为已经处理过的 token 保存 Key 和 Value。它不是只缓存一句话的字符串，而是缓存每一层计算出来的浮点张量。

粗略显存公式：

KV Cache 字节数 ≈
层数 × 2（K 和 V）× token 数 × KV 头数 × 每个头的维度 × 每个元素字节数

例如假设：

  • 32 层 Transformer
  • 8 个 KV heads（GQA）
  • 每个 head 维度 128
  • 上下文 8192 tokens
  • BF16，每个元素 2 字节
32 × 2 × 8192 × 8 × 128 × 2 bytes
≈ 1 GiB / 每条请求

这只是示例，实际还要考虑 batch、层数、KV head 数、数据类型、block 管理和其他运行时开销。

大白话：模型参数像厨师的固定工具，KV Cache 像每个顾客自己的草稿纸。顾客越多、对话越长，草稿纸越多。GQA 的作用之一，就是让 K/V 的头更少，从而减少这类草稿纸的大小。
可直接回答：KV Cache 主要按层数、序列长度、KV head 数和 head dimension 线性增长。GQA 通过减少 KV head 数降低缓存占用，所以在长上下文和高并发下尤其重要。估算时我会先用公式计算理论值，再结合实际可用显存、权重、激活和运行时预留判断最大并发。

六、TTFT、TPOT、E2E 到底分别是什么

指标意思用户感受主要受什么影响
TTFTTime To First Token，首 token 延迟。按下发送后，多久看到第一个字。Prompt 长度、Prefill 计算、排队、网络。
TPOTTime Per Output Token，平均每个输出 token 的时间。第一个字出来后，后续输出是否流畅。Decode、并发、显存带宽、采样和调度。
E2EEnd-to-End，总请求耗时。从发送到完整答案结束。排队 + Prefill + Decode + 网络。
注意口径：不同压测工具对 TPOT 是否包含第一个 token、是否去掉排队时间可能有差异。面试时要说清楚“本次测试的指标定义和统计口径”，不要只报一个数字。
面试回答：TTFT 主要反映用户等第一个字的时间，通常与 Prefill 和排队有关；TPOT 主要反映生成阶段的速度，通常与 Decode、显存带宽和并发有关；E2E 是完整请求耗时。性能优化前，我会先确认指标口径，再区分是排队、Prefill、Decode 还是网络造成的。

七、Prefill 和 Decode 的性能瓶颈

Prefill：一次读完整个输入

  • 输入 token 多时，计算量明显增加。
  • 更容易利用矩阵乘法并行计算。
  • 常见表现：TTFT 变长。
  • 常见优化：批量合并、FlashAttention、输入截断、Prefix Cache。

Decode：一个 token 一个 token 生成

  • 每一轮新生成的 token 很少。
  • 经常受显存读写和 KV Cache 访问影响。
  • 并发高时，KV Cache 和调度压力明显。
  • 常见优化：GQA、Continuous Batching、量化、PagedAttention。
一句话：Prefill 更像“快速读完一篇文章”，Decode 更像“边想边一个字一个字写答案”。前者容易受输入长度影响，后者容易受生成长度、并发和显存带宽影响。

八、Tensor Parallel 如何切分模型

Tensor Parallel，简称 TP，就是把同一层的大矩阵拆给多张卡同时计算，而不是每张卡都放一份完整模型。

以线性层 Y = XW 为例：

  • 列切分：把 W 按列切开，每张卡算一部分输出，最后拼接。
  • 行切分：把 W 按行切开，每张卡算一部分结果，最后做 All-Reduce 或求和。
卡 0：W 的一部分 → 局部结果
卡 1：W 的另一部分 → 局部结果
                         ↓
                 通信集合结果
可直接回答：TP 通过切分线性层、Attention 头或 MLP 的权重，让多张卡共同完成一层计算。它可以降低单卡权重和激活压力，但会引入 All-Reduce、All-Gather 等通信。卡间带宽和拓扑会直接影响扩展效率，所以不是 TP 越大越快。

实际模型的切分方式由框架实现决定，不能只凭模型名字猜。面试时可以结合具体模型的 attention heads、hidden size、TP size 和通信拓扑回答。

九、vLLM 与 vLLM-Ascend 的差异

可以把 vLLM 理解为推理引擎主体，把 vLLM-Ascend 理解为让这个主体适配昇腾 NPU 的后端和插件体系。

层次作用常见排障问题
vLLM请求服务、调度、KV Cache、模型执行流程。请求调度、结果拼接、采样、版本行为。
PyTorch模型代码和张量计算抽象。算子支持、dtype、shape、设备迁移。
torch-npu把 PyTorch 张量和算子接到昇腾设备。设备初始化、算子缺失、类型和布局问题。
CANN昇腾的软件栈，包括编译、运行时、算子和工具链。版本兼容、算子实现、编译或运行时错误。
HCCL昇腾多卡通信，类似多卡集合通信基础设施。All-Reduce、Rank、拓扑、通信超时。
面试回答：vLLM-Ascend 不是简单把 CUDA 改成 NPU。上层要保持 vLLM 的服务和调度行为，同时在设备抽象、算子实现、内存管理、多卡通信和模型兼容性方面适配 CANN、torch-npu 和 HCCL。遇到问题时，我会先判断是模型逻辑、PyTorch 设备层、算子、运行时还是通信链路的问题，再做最小复现。

十、27B、35B、122B 的硬件和压测怎么回答

最重要：不要凭模型参数量直接编造 GPU 数量、并发量或吞吐量。模型大小只决定一部分权重显存，KV Cache、量化、上下文长度、TP、硬件和版本都会改变结果。

面试官问“你怎么部署 122B”，可以按这个顺序回答：

  1. 确认模型版本、参数精度和量化方式。
  2. 估算权重显存：参数量 × 每参数字节数，再加运行时开销。
  3. 估算 KV Cache：层数 × KV heads × head dimension × 上下文长度 × 并发。
  4. 根据单卡显存、卡数和互联拓扑选择 TP 或其他并行方式。
  5. 先做单请求正确性，再做短输入、长输入、短输出、长输出的分组压测。
  6. 记录模型版本、驱动、CANN、torch-npu、vLLM、启动参数和数据集。
压测维度为什么要单独测
输入长度影响 Prefill 和 TTFT。
输出长度影响 Decode 和 E2E。
并发数影响调度、KV Cache 和排队。
精度 / 量化影响显存、算力、精度和算子支持。
TP size影响单卡压力和多卡通信。
安全回答模板：我不会只根据 27B 或 122B 判断部署规模。我会先确认精度、上下文和目标并发，再分别估算权重和 KV Cache，结合单卡显存与卡间互联选择 TP。压测时固定模型、数据集、版本和启动参数，分别记录 TTFT、TPOT、E2E、吞吐和显存使用，再做对照实验。

十一、Recall@5 从 60% 到 92% 怎么测

Recall@5 不是“模型回答准确率”，而是：正确资料是否出现在检索返回的前 5 条里。

准备一组带标准答案的查询：

问题 q1 → 标准相关文档集合 G1
检索 q1 → 返回前 5 条文档 R1

如果 R1 与 G1 有交集，则 q1 命中
Recall@5 = 命中的问题数 / 总问题数

举例：100 个测试问题中，有 92 个问题的正确制度出现在前 5 条结果里，那么 Recall@5 = 92%。

必须说清楚：是“问题级命中”还是“文档块级命中”？标准相关文档是 1 个还是多个？是否区分现行制度和废止制度？这些口径不同，数字不能直接比较。
面试回答：我们先建立带标准文档或条款的评测集，固定查询集和切分版本。对每个问题取 Top 5，检查标准文档或标准条款是否命中，最后统计命中问题数占总问题数的比例。优化前后保持同一评测集和指标口径，才可以说明 Recall@5 的提升来自检索链路改进。

十二、RAG 数据集、评测集和基线是什么

RAG 项目最好分成三套东西，不要混在一起：

对象它是什么用途
知识库文档真实制度文件、版本、元数据和权限。被切分、索引和检索。
评测集问题、标准文档、标准条款、参考答案和权限标签。衡量检索和回答质量。
基线系统最简单但可运行的初始方案。和优化后的方案进行公平对比。

一个合理的基线可以是：

原始文档 → 固定长度切块 → 向量检索 Top-k → LLM 直接回答

优化方案再逐步加入：

  • 标题、机构、日期、制度状态等元数据。
  • BM25 + 向量检索的混合召回。
  • RRF 融合和重排模型。
  • 查询改写、同义词和实体识别。
  • 现行制度过滤、权限过滤、引用校验和拒答。
面试回答：我会把 RAG 评测拆成检索质量、生成质量和安全性三部分。检索看 Recall@k、MRR 或命中率；生成看答案正确性、引用完整性和无依据内容比例；安全性看越权返回、废止制度误引用和敏感信息泄露。所有优化都要和固定基线及固定评测集对比。

十三、Beam Search token 问题怎么定位

这类问题不要一上来就改代码。先把“模型生成了什么”和“框架最终返回了什么”分开。

  1. 固定输入：固定模型、Prompt、tokenizer、dtype、seed 和生成参数。
  2. 对照运行：比较 greedy、sampling、beam search，以及离线和服务模式。
  3. 打印 token id：记录 Prompt token、生成 token、EOS、长度和 beam 数。
  4. 定位阶段：判断异常发生在模型输出、beam 重排、结果拼接、停止条件还是 decode。
  5. 检查重复拼接：有些结果对象已经包含 Prompt，有些只包含新生成 token，不能盲目再次拼接。
  6. 写最小测试：覆盖普通生成、beam search、EOS、达到 max tokens 和空输出。
输入 Prompt tokens:       [101, 2054, ...]
模型新生成 tokens:         [2023, 2003, ...]
框架最终 returned tokens:   [101, 2054, ..., 2023, 2003, ...]

如果最终结果已经包含 Prompt，不能再做：
Prompt + returned_tokens
否则会出现 Prompt 重复或 token 长度异常。
可直接回答：我会先用固定输入复现，再在 tokenizer、模型输出、beam 重排、停止条件和结果封装边界分别打印 token id。重点确认返回对象表示的是完整序列还是仅新生成序列。修复时只调整结果处理边界，并用普通生成、beam search、EOS 和 max token 等回归用例验证，避免只修复一个样例。

十四、面试时如何诚实地回答“你到底做了多少”

你目前正在通过课程补齐基础，不需要假装自己已经把所有实现细节都独立完成。推荐使用四段式：

  1. 背景：这个项目解决什么问题。
  2. 职责：你亲自负责哪一部分。
  3. 方法：你怎么验证、怎么定位、怎么做对照。
  4. 结果与边界：指标变化是什么，还有哪些部分不是你独立负责的。
示例：“我主要负责推理链路测试和问题定位，不是从零实现整个 vLLM。遇到 Beam Search 结果异常时，我先固定输入并比较 token id，确认问题发生在结果处理阶段，再修改只提取 Decode 阶段新 token 的逻辑，最后补了普通生成和 Beam Search 的回归用例。”
不要这样回答：“vLLM 我都懂”“RAG 准确率就是 91%”“122B 我负责完整部署”。这些说法很容易被一个细节问题击穿。
