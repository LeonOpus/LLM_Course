Lesson 14：Agent 开发

从会调用工具的模型，走向能规划、执行、复盘和积累经验的应用。

一句话：把复杂问题拆成可执行的小任务，让程序协调模型、检索和工具，并通过状态、质量检查与记忆管理把结果串起来。

4. 一次深度研究请求怎么走？

  1. 规划：Orchestrator.decompose_task 要求模型输出查询类型、研究计划和子任务，解析成 TaskPlan、SubTask。
  2. 分工：dispatch_workers 在线程池里运行多个 Worker，按完成顺序收集结果。工作线程可以同时发起搜索；实际速度仍受接口、网络和限流影响。
  3. 单个 Worker：SearchWorker.execute 运行 OODA：观察搜索结果、判断信息缺口、决定继续或停止、安排下一步。代码中搜索次数与循环次数有预算。
  4. 汇总与检查：协调者把结果交给模型合成报告，调用质量检查，再根据分数、迭代次数和停止条件决定结束或补充研究。

这里的质量分数是模型或规则给出的辅助信号，不自动证明事实正确。尤其需要检查引用是否真实、原文是否支持结论、多个来源是否独立。

代码阅读发现：API 处理不同请求时临时修改共享的全局配置，并发任务可能互相影响；线程池通过 as_completed 收集已完成任务后再调用 future.result(timeout=...)，不能据此认定单个 Worker 已被可靠限时。生产化需要改为任务级配置与真正的超时/取消机制。

5. 三种 Agent 编排怎么选？

方式直觉与适用情况代价
固定链 / Workflow步骤基本确定，像流水线；适合规则明确的任务，容易控制和测试。灵活性有限，意外情况需要显式分支。
ReAct / 反思循环根据观察决定下一步工具或修正动作，适合执行路径不能预先完全确定的任务。可能重复调用、耗时或跑偏，要有上限和终止规则。
协调者 + 多 Worker把可拆分的子任务交给不同 Worker，再统一汇总；适合多个研究角度可并行的场景。合并冲突、协调成本、上下文传递和服务并发更复杂。

第三周金融项目在 agents/graph.py 中用 LangGraph 表示 Router → Planner → Executor → Reflector → Critic，并用条件边控制继续执行或重新规划。本次是代码阅读，未运行该 LangGraph 项目。

6. 记忆、RAG 和工具的区别

RAG 给当前问题找外部知识：文档切片、向量化、检索后放入提示词。记忆 保存与用户或过去任务有关的信息，以便将来召回。两者都可能用向量检索，但关注的数据和使用目的不同。

第四周的 MemoryPipeline 使用进程内列表作为短期缓冲，达到阈值后保留最近两条、尝试摘要并存入 Milvus；之后可检索长期记忆和压缩上下文。课程规划提到 Redis，但不能因此说这个缓冲已经由 Redis 持久化。本次没有运行 Milvus 记忆链路。

DreamingService 的设计是对已有记忆做聚类、去重、提取洞见和处理冲突；摘要或洞见可能丢信息、过时或错误，需要保留可追溯来源、隔离不同用户并提供纠正和删除能力。

第三周的 Text2SQL 把模型生成的 SQL 交给数据库执行。真实生产环境必须约束只读权限、查询范围和超时，不能只依赖提示词；代码执行也需要隔离，课程的能力描述不等于已经通过安全验证。

7. 第五周：轨迹和训练

一条训练样本通常是 system → user → assistant 工具请求 → tool_response → assistant ...。它记录的是模型每一步该如何行动，而不只是最后的答案。

data_loader_v2.py 把 tool_response 转为带“工具返回”标记的 user 消息；再应用聊天模板，将非 assistant 部分标签设为 -100。该加载器尝试监督多个 assistant 内容区间；Lesson 13 的验证是只监督最后一个 assistant。截断、模板兼容性和监督区域必须在换模型后重新检查，特别是截断可能导致监督为空。

训练结束只得到适配器，需要配合基础模型使用。模型能学会输出工具格式，并不等于能够可靠选择工具或正确使用真实结果；需要用独立测试集和真实工具测试。

10. 面试表达

30 秒

我研究了一个深度研究 Agent 的实现：协调者先把问题拆成子任务，多个 Worker 并行搜索和分析，再汇总报告、检查质量并按预算决定是否继续。我在本机用模拟模型和搜索验证了并行与完整调度流程，也用课程轨迹完成了两步 LoRA 训练。真实 API 和业务效果还没有验证。

2 分钟

我的理解是，Agent 的关键是把模型决策放进可控的程序循环。这个项目的协调者负责规划、分发和汇总；Worker 在搜索预算内执行观察、分析、决策和后续行动。状态结构保存任务、结果与迭代信息，API 对外暴露状态和进度。另一个金融示例使用状态图控制执行与反思；记忆示例把近期对话归档成长期摘要，再按相关性取回。训练部分使用多轮工具轨迹，mask 非 assistant 内容，通过 LoRA 更新少量参数。

验证方面，我跑了前端构建、独立 API 健康检查、模拟研究调度、1,140 条轨迹规则校验和本地两步训练。实际工程仍需做独立评测、真实接口联调、任务隔离、超时和引用核验；这些不应当用模拟通过来代替。

追问

为什么并行？相互独立的子任务可以重叠等待时间，但会增加接口并发、费用和结果整合成本。

怎么评估 Agent？按任务成功率、工具选择与参数、引用可核验性、延迟、费用和失败恢复分别评估，并用独立数据集验证。

怎么防止无限循环？设定调用次数、迭代次数、总耗时和费用预算；结果不改善或工具反复失败时明确停止并反馈。
