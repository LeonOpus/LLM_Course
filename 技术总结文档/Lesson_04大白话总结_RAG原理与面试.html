Lesson 4：RAG 原理与面试大白话总结

Retrieval-Augmented Generation：先找资料，再让大模型根据资料回答

一句话理解：RAG 不是重新训练大模型，而是给大模型配了一个“会查资料的外接记忆库”。用户提问后，系统先从自己的文档库里找相关片段，再把片段放进 Prompt，最后让大模型回答。

二、RAG 的完整流程

离线阶段：文档 → 解析 → 清洗 → 切块 → Embedding → 建索引

在线阶段：用户问题 → 查询改写/理解 → 召回 → 重排 → 上下文拼装
                              ↓
                     LLM 根据资料生成答案
                              ↓
                       引用、校验或拒答
步骤大白话代码里通常是什么
文档解析把 PDF、网页、Word 变成文字。PyMuPDF、SimpleDirectoryReader、LlamaParse。
切块 Chunking把一本书拆成很多张“资料卡片”。固定长度、递归、语义分块、命题分块。
Embedding把文字变成能计算相似度的数字坐标。OpenAI Embedding、本地 Embedding 模型。
召回 Retrieval从几千张资料卡里先找一批可能相关的。向量检索、BM25、混合检索。
重排 Rerank把初选结果再按问题逐条精排。Cross-Encoder 或 LLM 重排。
增强生成把相关资料塞进 Prompt，让模型只根据资料回答。Context + Question + Answer Prompt。
面试回答模板：RAG 主要分为索引构建和在线问答两阶段。索引阶段完成文档解析、切块、向量化和索引；问答阶段对用户问题做查询处理，召回候选片段，必要时重排和压缩，再把高相关上下文交给 LLM 生成答案。效果差时要分别排查解析、切块、召回、重排、Prompt 和生成，不能只怪模型。

三、为什么切块是 RAG 的核心难点

大模型不能每次把整本 PDF 都塞进去。文档必须切成适合检索的小片段，但切得太粗、太细都不好。

切得太大

  • 相关内容被噪声包围。
  • 同样的上下文长度能放更少的片段。
  • 最终 Prompt 变长，成本和延迟增加。

切得太小

  • 一个事实被拆散。
  • 片段缺少标题和章节背景。
  • 检索到了句子，却不知道它属于哪个主题。

Overlap 重叠：相邻文本块保留一小段重复内容，避免一句话刚好被切在边界上。Overlap 不是越大越好，太大会造成重复召回和存储浪费。

语义分块：不是机械地每 500 字切一次，而是观察句子之间的语义变化，主题明显变化时再切。

命题分块：把一段复杂描述改写成若干条独立事实。例如“公司于 2024 年在深圳成立，主营……”可以拆成成立时间、成立地点和主营业务三个命题。

大白话：切块就是整理资料卡。卡片上既不能写整本书，也不能只写半句话；最好保留“这是哪份文档、哪一章、讲什么、具体事实是什么”。

四、Embedding 到底做了什么

Embedding 模型把一段文字变成向量，例如：

“如何申请年假？” → [0.12, -0.08, 0.44, ...]
“员工休假申请流程是什么？” → [0.11, -0.07, 0.42, ...]

两个向量距离较近 → 语义上可能相似

向量检索比较的是“语义相似度”，所以“年假怎么申请”和“休假审批流程”即使字面不同，也可能找到同一段资料。

Embedding 不等于答案：它只是把文本放到向量空间里，负责找相似资料，不负责最终回答，也不等于知识已经写进模型参数。

常见问题：

  • Embedding 模型不适合中文或领域术语。
  • 问题和文档使用不同表达，导致向量相似度不稳定。
  • 向量库中的文档版本过期。
  • 没有保存文档来源、页码、机构、时间等元数据。

五、向量检索、BM25 和混合检索

方法擅长什么短板
向量检索理解语义相近、同义表达和概念关系。专有名词、编号、精确数字不一定稳定。
BM25匹配关键词、编号、产品名和精确术语。不理解深层语义，同义改写可能匹配不到。
混合检索同时利用关键词和语义，通常更稳。要处理两种分数的尺度和融合策略。

BM25 可以理解为“关键词打分”：某个词在当前文档出现得多、在全部文档里又不常见，这个词对相关性贡献更大。

RRF 融合：不强行比较 BM25 分数和向量分数，而是按照各自排名给奖励，再把排名奖励相加。它适合解决两套分数不能直接比较的问题。

BM25 排名：文档 A、C、B
向量排名：文档 B、A、D
融合后：A 和 B 同时进入前排，C、D 按各自排名继续竞争
面试回答模板：关键词检索对编号、实体和精确词很强，向量检索对同义表达和语义相似更强。实际系统通常先用 BM25 和向量检索分别召回，再用 RRF 或其他方法融合，最后交给重排模型做更精细判断。

六、为什么召回后还要重排和上下文压缩

第一阶段召回追求“别漏掉”，所以可以取 Top 20 或 Top 50；第二阶段重排追求“把最相关的放前面”，再只取 Top 3～8 给大模型。

全部文档 100,000 篇
      ↓  向量/BM25 快速召回
候选 50 个片段
      ↓  Cross-Encoder / LLM 精排
最终 5 个高相关片段
      ↓
放入 Prompt 生成答案

上下文压缩：检索到的片段可能有大量无关句子。压缩器只保留与问题相关的句子，减少上下文噪声、Token 消耗和模型被干扰的概率。

大白话：召回像图书馆管理员先拿来 50 本可能相关的书；重排像专家快速翻这 50 本，挑出最相关的 5 本；上下文压缩像把这 5 本书中真正有用的段落划出来。

七、查询转换：不要总拿用户原话直接搜

技术作用例子
Query Rewrite把口语问题改写成更适合搜索的表达。“这东西咋报销”→“差旅费用报销条件和流程”。
Query Decomposition把复杂问题拆成多个子问题。先找政策，再找适用人群，最后比较时间。
Step-back Query先退一步问更一般的背景问题。先检索“什么是 LoRA”，再回答具体配置问题。
HyDE先让 LLM 写一段假设答案，再用假设答案去检索。适合短问题和长文档之间表达差距较大的场景。
HyDE 的风险：假设答案本身可能是错的。如果把错误假设当事实使用，可能把检索带偏，所以要和普通检索做对照评测，不能默认它一定更好。

八、RAG 怎么评测，不能只说“感觉更准了”

指标大白话关注哪一段
Recall@K正确资料有没有出现在前 K 个结果里。召回是否漏资料。
Precision@K前 K 个结果里有多少是真相关。召回是否混入太多噪声。
MRR第一个正确结果排得有多靠前。正确资料出现的位置。
nDCG多个结果的相关程度和排序是否合理。排序质量。
Faithfulness答案是否能被检索资料支持。是否胡编。
Answer Relevancy答案是否真正回答了问题。是否答非所问。

Recall@5 的简单计算：

100 个问题，每个问题都有标准相关文档
检索 Top 5 后，92 个问题命中了标准文档
Recall@5 = 92 / 100 = 92%

评测集至少应保存：

  • 用户问题。
  • 标准相关文档或条款。
  • 参考答案。
  • 文档版本、机构、权限和生效状态。
  • 是否允许拒答。
面试回答模板：我会把 RAG 评测分成检索、生成和安全三部分。检索看 Recall@K、MRR；生成看答案正确性、引用完整性和 Faithfulness；安全看越权返回、废止制度误引用和无依据内容。优化前后固定同一评测集、文档版本和指标口径，用基线做对照。

十、LlamaIndex 在 RAG 中是什么角色

LlamaIndex 不是大模型，也不是向量数据库。它更像一个 RAG 应用编排框架，帮你把数据读取、节点切分、Embedding、索引、Retriever、Query Engine 和 LLM 串起来。

SimpleDirectoryReader
        ↓
Document / Node
        ↓
VectorStoreIndex
        ↓
Retriever
        ↓
QueryEngine
        ↓
LLM 回答

如果面试官问“自己实现和 LlamaIndex 有什么关系”，可以回答：

自己实现能看清每一步的输入输出和指标，方便控制切块、检索、过滤和权限；LlamaIndex 提供了成熟的组件抽象，适合快速搭建和替换模块。生产系统不能只会调用框架，还要理解框架内部的索引、检索和 Prompt 链路。

十一、面试高频回答

1. RAG 和 Fine-tuning 有什么区别？

RAG 是在推理时临时查资料，不改变模型参数，适合知识更新快、需要引用和权限控制的场景；Fine-tuning 是训练模型参数，适合稳定的行为、格式和领域能力。RAG 解决“模型不知道最新资料”，微调主要解决“模型不会按要求做”。两者可以结合。

2. RAG 效果差，你怎么排查？

我会按链路排查：先确认文档是否解析完整，再检查切块是否保留标题和上下文，然后单独评估召回 Recall@K，接着看重排和上下文长度，最后检查 Prompt、模型能力和答案校验。通过固定评测集和日志，把检索错误与生成错误分开。

3. 为什么不能只用向量检索？

向量检索擅长语义相似，但对制度编号、股票代码、产品型号、精确数字等关键词不一定稳定；BM25 对精确词很强。混合检索可以同时利用语义和词法信息，再通过 RRF 或重排统一排序。

4. 怎么防止 RAG 胡编？

先提升召回和重排质量，再在 Prompt 中要求只依据上下文回答；对引用的文档、页码和条款进行校验；相关性不足时拒答；用 Faithfulness、无依据内容比例和引用正确率评估。RAG 不能保证绝对不胡编，只能通过链路和评测降低风险。

5. RAG 为什么要做权限过滤？

因为检索结果本身可能泄露用户无权访问的资料。权限最好在检索前按机构、岗位、密级做过滤，生成后还要校验引用和输出，不能只在最终 Prompt 里提醒模型“不要泄露”。

6. 你的 RAG 项目最有价值的工程点是什么？

不要只说“用了向量数据库”。应该讲清楚文档版本和状态、元数据、混合检索、重排、引用校验、拒答、权限控制以及评测集。真正的项目难点通常不是把 Demo 跑起来，而是让系统在资料更新、权限变化和错误问题下仍然可靠。
