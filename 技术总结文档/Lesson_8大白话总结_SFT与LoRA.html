1. 一句话：这个实验解决什么问题？

用本机已有的 Qwen2.5-1.5B-Instruct 和课程问答数据，跑通一次只训练少量 LoRA 参数的监督微调，理解模型如何学习按照问题生成期望回答。

大白话：它和 Lesson 7 的关系

Lesson 7 让模型通过大量文本学习“下一个 token 是什么”，逐步形成语言能力。Lesson 8 给模型看“用户这样问，助手可以这样回答”的示例，继续调整参数，让输出更贴近某种任务、风格或格式。

训练的底层仍然是预测下一个 token；变化主要在于使用的模型起点、数据组织方式和需要监督的位置。我们这次使用的是已经过指令训练的 Instruct 模型，不是从零训练，也不能据此声称训练后模型一定更好。

和 Lesson 5 的 RAG 对比：RAG 通常在回答时临时检索外部材料，不需要因为每条新资料更新模型权重；SFT 是通过训练改变模型参数或增量参数。二者可以组合，用来解决不同问题。

课程问答数据（query、answer）→ 对话模板 → token ID

3. 一条 SFT 数据怎么进入模型？

数据文件每行是一个 JSON 对象，关键字段是 query（问题）与 answer（示范回答）。SFTDataset 将 system、user、assistant 消息按模型的 chat template 编成序列。

示意对话：
[system] 你是一个有帮助的助手
[user]   三原色是什么？
[assistant] 三原色包括……

input_ids：[系统和问题的 token … 助手起始标记 … 回答 token …]
labels：   [-100, -100, … -100, 回答 token …]

这是示意，不是模型真实的 token ID。脚本先单独构造包含助手起始标记的前缀，再构造完整对话，并验证前缀确实与完整序列开头一致；不一致时直接报错，避免错把问题或模板内容当成回答标签。

为什么标签用 -100？

在这里，Hugging Face 因果语言模型使用的交叉熵忽略标签为 -100 的位置。系统提示、用户问题和补齐位置不直接计入 loss；回答 token 是监督目标。被屏蔽的提问仍然作为上下文输入模型，不是从输入中删除。

模型内部会处理因果语言模型所需的标签错位。批处理时 attention_mask 区分真实 token 和 padding；labels 中的 -100 控制哪些位置计入 loss，两者用途不同。

实际检查的一条样本中，有 25 个前缀 token 被屏蔽、167 个回答 token 参与监督。默认最大长度为 256；超长内容会被截断，如果整个回答都被截掉，样本会被跳过。截断也可能让较长回答只保留前半段。

4. LoRA：为什么只训练一小部分参数？

LoRA（低秩适配）的直觉是：先保留模型原有能力，在指定线性层旁边增加一个较小的可训练分支。训练时主要调整这个分支，推理时基础模型和增量一起参与计算。

W有效 = W原始 + ΔW
ΔW = (α / r) × B × A

W原始：[d_out, d_in]
A：   [r, d_in]        B：[d_out, r]
B × A：[d_out, d_in]

其中 d_in、d_out 是该线性层的输入和输出维度，r 是低秩维度，α 是缩放系数。当 r 相比输入输出维度较小时，A 和 B 的参数量 r × (d_in + d_out) 通常少于完整矩阵的 d_in × d_out。这是标准 LoRA 的解释；完整模型有多个被适配的线性层。

本次实际参数：r=8、lora_alpha=16、dropout=0.05，目标模块是注意力中的 q_proj 和 v_proj。打印结果显示可训练参数 1,089,536，全部参数 1,544,803,840，约 0.0705% 可训练。

LoRA 和 QLoRA 不一样：本次基础模型以 BF16 加载，没有做 4-bit/8-bit 量化。这是 LoRA 实验；QLoRA 通常结合低比特量化基础权重与 LoRA，不能仅因为用了 LoRA 就叫 QLoRA。

5. 关键 shape、损失与训练

假设 batch 大小为 B、本批序列长度为 T、词表大小为 V：

对象shape含义
input_ids[B, T]对话 token 的整数编号。
attention_mask[B, T]标识有效输入和补齐部分。
labels[B, T]前缀和 padding 为 -100，回答部分为目标 token。
logits[B, T, V]每个位置对词表各 token 的未归一化分数。
loss标量根据有效回答位置的预测误差计算。

脚本依次执行 model(**batch).loss、loss.backward()、optimizer.step()。优化器只接收 requires_grad=True 的参数；每步更新后梯度会在下一步开始前清空。

本次 batch size 为 1，实际设置最多读取 8 条样本，按原顺序训练 4 步；因此本次只使用了前 4 个有效样本，不能说训练了全部 8 条。

8. 为什么这样设计？代价与改进方向

方案收益代价或限制
只监督回答训练目标集中在助手应该生成什么。标签边界必须和对话模板一致；截断可能让回答不完整。
LoRA训练和保存的参数较少，适合资源受限的实验。仍需加载基础模型；目标层、秩和数据质量会影响效果，不保证优于全量微调。
Instruct 模型继续 SFT在已有指令能力上适配特定行为或格式。可能改变原有能力；需要评估任务效果、遗忘和安全表现。
小样本试运行快速确认代码、显存和保存加载流程。没有足够训练量或独立评测，不能判断实际能力。

想评估是否有效，应准备训练集和独立验证/测试集，避免相似样本泄漏；比较微调前后同样问题、同样生成配置下的结果，再结合业务指标、人工评价与失败案例。领域任务还需要审查数据质量、隐私、来源和过时内容。

2 分钟

微调是在已有模型基础上继续用任务数据训练，让模型更贴近目标输出；底层仍是自回归预测。这个实验使用课程问答数据，先通过模型的 chat template 组织 system、user 和 assistant 消息，再屏蔽前缀及 padding 标签，只对回答计算交叉熵。模型使用 PEFT 添加 LoRA，只训练 Q、V 投影上的低秩增量，参数比例约 0.0705%，完成 4 步更新后保存 adapter。

我还重新加载基础模型和 adapter 做了生成验证。课程原脚本使用 Windows 上的 Llama 路径，我把它适配成本机 Qwen 1.5B。这个实验没有使用量化，也不是课程的医疗或法律模型完整复现；由于测试问题来自训练数据且没有独立评测，不能声称性能提高。

追问速答

  • SFT 和预训练的差别？两者都可用下一个 token 预测；SFT 更强调指令与目标回答的数据组织，以及希望监督哪些输出位置。
  • 为什么问题 labels 为 -100？让问题作为上下文输入，但不对它计算该实验的训练 loss；回答位置仍然有监督。
  • LoRA 为什么省资源？冻结大部分基础参数，只训练低秩增量，减少可训练参数和相应优化器状态；基础模型本身仍要加载。
  • LoRA 是不是 QLoRA？不是。QLoRA 通常还使用低比特量化基础模型；本次是 BF16 基础模型加 LoRA。
  • 怎么判断微调是否有效？固定基础模型、测试集和生成设置，对比微调前后，结合业务指标、人工评价和错误案例。
  • adapter 能单独运行吗？通常不能；它保存增量参数和配置，推理时需加载匹配的基础模型，或采用兼容的合并流程。
  • 训练样本太长怎么办？明确截断或分段策略，检查回答是否被截断，统计有效监督 token，并根据资源调整长度。
