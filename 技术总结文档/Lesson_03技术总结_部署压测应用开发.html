二、先用一句话理解整节课

用户请求 → FastAPI 接口 → 参数校验 → 组织 Prompt → 调用 LLM → 流式返回 → 必要时调用工具/生成图片 → Redis 缓存 → 前端展示

你可以把它想成一家餐厅：

  • FastAPI 是前台点餐窗口。
  • Pydantic 是检查订单格式的服务员。
  • LLM Service 是后厨的大厨。
  • Function Calling 是大厨发现自己需要查天气，于是让工具去查。
  • SSE 是后厨做好一道菜就先端一道，而不是全部做完才一次性上菜。
  • Redis 是小黑板：相同问题以前做过，就不用重新做。
  • 压测 是模拟突然来了很多桌客人，看系统会不会堵住。

三、FastAPI：把 Python 函数变成 HTTP 接口

最基本的 FastAPI 应用就是：创建一个 app，用装饰器把 URL 绑定到函数。

from fastapi import FastAPI

app = FastAPI()

@app.get("/health")
async def health():
    return {"status": "ok"}

启动后，浏览器或前端可以访问：

uvicorn main:app --host 127.0.0.1 --port 8000

面试里要说清楚：

  • FastAPI 是 Web 框架，负责路由、参数解析、校验和返回响应。
  • Uvicorn 是 ASGI 服务器，真正负责接收网络请求、运行异步应用。
  • async def 适合 I/O 等待明显的场景，例如等待 LLM、数据库、Redis 或其他 HTTP 服务。
  • 异步不是让 CPU 计算变快，而是等待网络时可以处理其他请求。

Pydantic：为什么接口不容易收到脏数据？

class QuestionRequest(BaseModel):
    subject: str = "general"
    text: str
    stream: bool = True

前端传 JSON 后，FastAPI 会自动把它转成模型对象，并对类型、必填字段、枚举值进行校验。校验失败时返回 422，而不是让错误数据一路传到模型服务。

四、Function Calling：模型不能真的“执行函数”

Function Calling 的真实含义不是模型自己运行 Python。模型只是输出一个结构化的“工具调用请求”，真正执行函数的是你的后端。

用户问题 → 模型决定需要工具 → 返回函数名和参数 → 后端执行函数 → 把结果放回对话 → 再请求模型生成自然语言答案

课程里的天气示例可以拆成 5 步：

  1. 用户问：“巴黎今天多少度？”
  2. 模型判断需要调用 get_weather(latitude, longitude)。
  3. 后端解析模型给出的 JSON 参数。
  4. 后端请求天气 API，得到温度。
  5. 后端把工具结果作为 tool 消息传回模型，模型再组织最终回答。
面试回答：Function Calling 是让模型输出结构化工具意图，由应用层负责参数校验和真实执行，再把工具结果回传给模型。模型负责决策和生成，业务代码负责执行和安全边界。

安全重点：工具参数必须校验，不能让模型直接执行任意 Shell 或任意 Python；工具应设置白名单、超时、权限和错误处理。

五、SSE 流式输出：为什么答案能一个字一个字出现？

普通接口是“模型全部生成完 → 一次性返回”。流式接口是“生成一小段 → 立刻推给前端”。课程项目使用的是 SSE（Server-Sent Events）风格的数据流。

data: {"type":"text","content":"你好"}

data: {"type":"text","content":"，我来"}

data: {"type":"done","content":"处理完成"}

后端常见写法是异步生成器：

async def stream_answer():
    yield "data: {\"type\":\"start\"}\n\n"
    async for chunk in llm_stream():
        yield f"data: {chunk}\n\n"
    yield "data: {\"type\":\"done\"}\n\n"

注意：流式输出主要改善首字响应时间和用户体验，不一定降低模型总计算量。它还会带来连接管理、断线重连、结束事件、异常事件和前端拼接等工程问题。

六、Prompt 工程：不是“写得越长越高级”

Prompt 工程的核心是把模糊需求变成可执行的任务说明。一个稳定的 Prompt 通常包含：

部分大白话例子
角色你希望模型以什么身份工作你是一名 Python 代码审查助手
任务最终到底要做什么找出 bug 并给出修复建议
输入背景模型需要知道什么代码运行环境是 Python 3.12
约束什么不能做，格式是什么只输出 JSON，不要解释
示例给模型一个参考样板One-shot / Few-shot
验收标准什么结果算合格字段齐全、可解析、无 Markdown 包裹

Zero-shot 是不给例子；One-shot 是给一个例子；Few-shot 是给多个例子。例子不是越多越好，应该覆盖最容易出错的格式和边界情况。

课程 Notebook 中出现了“让模型展示思维链”的写法。工程上更推荐要求简短的可验证步骤、结论或结构化字段，不要把暴露详细内部推理过程当成系统依赖。

七、多轮对话：记忆其实是你自己维护的消息列表

API 通常不会因为你调用了两次就自动知道第一次说了什么。应用要把历史消息继续传入：

conversation = [
    {"role": "developer", "content": "你是 Python 助手"},
    {"role": "user", "content": "什么是列表？"},
    {"role": "assistant", "content": "列表是一种有序容器……"},
    {"role": "user", "content": "那如何遍历它？"}
]

历史太长时不能无限拼接，需要做截断、摘要、向量检索或持久化。生产系统还要给每个用户、会话和消息设置 ID，避免不同用户的对话串线。

八、压测：不要只看“能不能返回 200”

压测.py 面向 OpenAI-compatible 的 /v1/chat/completions 接口，关注的指标包括：

上下文上限

输入过长时什么时候报错或被截断。

输出上限

允许设置的最大输出和默认最大输出。

RPS

每秒可以完成多少请求。

TPS

每秒生成多少 token，反映生成速度。

并发数

多少个请求同时进来还能稳定运行。

错误率

429、5xx、超时和断流都要统计。

压测不是把脚本一运行就结束。要控制变量：固定模型、固定输入输出长度、逐步增加并发、记录 P50/P95/P99 延迟、错误率和 GPU 显存。

面试回答：LLM 压测要同时看吞吐和延迟。Prefill 阶段更受输入长度和计算吞吐影响，Decode 阶段更受 KV Cache、显存带宽和并发影响。实际评估不能只看平均响应时间，还要看长尾延迟、错误率、首 token 延迟和生成 token 速度。

九、“深学 AI”项目：从 Notebook 变成微服务

这个项目把功能拆成两个后端服务：

服务负责什么为什么拆开
answer-service接收问题、调用百炼、流式返回答案、编排可视化问答逻辑变化不会影响绘图服务
viz-service判断是否需要画图、生成函数/几何图、提供图片绘图依赖和计算可以独立扩缩容
Redis缓存结果、保存短期状态、减少重复调用降低延迟和 LLM 费用
React 前端登录、聊天、Markdown、公式、图片展示通过 HTTP/SSE 与后端解耦
React → answer-service /v1/ask → LLM；answer-service → viz-service /v1/check、/v1/generate；两者共享 static 图片目录；Redis 负责缓存。

依赖注入就是路由函数不自己创建所有对象，而是由统一依赖函数提供 Redis、编排器、LLM 服务。这样方便测试、替换实现和管理生命周期。

十二、建议你记住的面试表达

问：如何把大模型接入业务？
答：我会把模型调用封装成独立适配层，由 FastAPI 提供接口，Pydantic 做参数校验，业务层编排 Prompt、工具调用和缓存，使用 SSE 返回流式结果，并通过超时、重试、限流和日志保证可观测性。

问：Function Calling 是模型执行函数吗？
答：不是。模型只返回结构化工具意图，后端验证参数并执行真实函数，再把结果回传模型生成最终回答。

问：为什么要流式输出？
答：模型生成是逐 token 的，SSE 可以把已经生成的片段及时推给前端，降低用户感知的首字延迟；但它需要处理连接、断线、结束事件和异常事件。

问：怎么压测 LLM 服务？
答：固定模型和输入，逐步增加并发，记录首 token 延迟、总延迟、生成 TPS、吞吐 RPS、P95/P99、429/5xx 和显存。还要分别考虑 Prefill 和 Decode 的瓶颈。

问：Redis 在项目中做什么？
答：缓存高频或重复请求的结果、保存短期会话状态，并通过 TTL 和淘汰策略控制内存；缓存键必须包含用户、模型、Prompt 版本等必要信息，避免串数据。

十三、你可以按这个顺序继续学习

  1. 先运行 FastAPI 四章，熟悉路由、参数、Pydantic、异步和中间件。
  2. 再看 02_Function_Call.ipynb，配置 API Key 后完整跑通“模型决定调用工具 → 后端执行 → 回传结果”。
  3. 再看提示词 Notebook，把重点放在结构化输出、Few-shot、角色约束和多轮消息管理。
  4. 最后阅读“深学 AI”后端，沿着 /v1/ask 路由追到编排器、LLM 服务、Redis 和可视化服务。
  5. 有了一个可用的 OpenAI-compatible 服务地址后，再运行 压测.py，先把并发上限从 128 调小，避免误产生大量请求费用。
本课最重要的一句话：大模型应用工程不是“会调用一次 API”就结束，而是要把模型、工具、接口、流式传输、缓存、错误处理、并发和前端体验组织成一条稳定的业务链路。
