1. 项目一句话

SalesPilot 是一个面向新能源车销售培训的助手项目，尝试结合产品文档检索、网络搜索和 Agent，为销售人员组织产品问答与销售话术。

大白话：这一课比 RAG 多了什么？

Lesson 5 主要在解决：从文档里找相关材料，再让模型参考材料回答。这节课继续往前走：如果问题需要不同来源，系统尝试先让模型决定“要查什么、用什么工具”，执行搜索后再整理答案。

可以把 Agent 想成一个会使用工具的助手：接到任务后先列计划，调用本地检索或网络搜索，收集结果，再判断是否需要补查，最后组织回答。这里的“规划”和“反思”是模型根据提示词生成文本，由程序解析和执行，并不意味着模型自己直接操作数据库或浏览器。

连接上一课：RAG 是这里可调用的一种工具；Agent 是协调工具和步骤的程序流程。两者可以组合，也不是所有 RAG 都需要 Agent。

2. 先看全局：一次请求经过哪里？

浏览器 React 页面 → Vite 代理 /ai-search → FastAPI 后端
                               ↓
          普通搜索 /ai_search/       深度探索 /deep_research/
          文档检索 + 网页搜索           规划 → 工具执行 → 反思 → 生成
                               ↓
             百炼模型接口 / Serper 搜索 / Elasticsearch / PostgreSQL
                               ↓
                     SSE 流式返回 → 页面逐步显示

前端负责接收输入和展示结果；FastAPI 负责路由与业务编排；Elasticsearch 在项目中承担文档检索；PostgreSQL 保存用户及部分会话、消息等结构化数据。具体路径的保存行为不同，不能认为所有请求都会存历史。

两条路径要分清

路径代码中的主要步骤理解重点
普通搜索 /ai_search/检查知识库 → 有则检索 → 读取历史问题 → 搜索网页 → 拼 Prompt → 模型流式回答。这是固定编排的检索与生成路径；流结束分支中有写入对话和更新会话名的代码。
深度探索 /deep_research/把问题交给 final_answer，按计划调用工具，尝试反思，然后流式生成。这是本课观察 Agent 编排的主要入口；该入口接收 session_id，但当前实现没有把它传给 final_answer。

4. 深度探索：像跟着一次请求走代码

用“星辰电动 ES9 有智能座舱吗？”举例。以下是代码预期流程，示例问题和结果用于解释，实际模型输出可能不同。

第一步：规划 Plan

agent_plan(query) 把用户问题、可用工具、选工具的规则写进 Prompt，调用 middle_json_model 请求百炼的 qwen-plus。程序再试图从返回文本提取 JSON 列表。

示意规划：
[{"action_name": "本地文档搜索", "prompts": ["ES9 有智能座舱吗？", "座舱有哪些功能？"]}]

直觉：先写一张“待办清单”。准确说：模型输出的是约定格式的文本，能否解析以及选择是否合理，都需要程序处理和验证。

第二步：拆成一个个动作并执行

adjust_format 把一个工具下的多个问题拆成多个 {action_name, prompt}。process_actions 遍历这些动作：本地文档搜索走 rag → retrieve_content；网络搜索走 web_search_answer → Serper。每次结果放入当前请求的 memory，并尝试对含 content_with_weight 的内容去重。

这个 memory 是本次执行中临时组织的检索结果，不等于持久化的长期记忆，也不等于 KV Cache。

第三步：反思 Reflection

reflection(user_query, memory_global) 再次请求模型判断现有材料是否足够，尝试返回补充查询。设计目的是“查完看看还有什么缺口”，但实际执行存在下面两点代码限制。

读代码发现的具体问题：
① memory_global.extend(list(memory_new)[1:]) 会跳过第一项检索结果；只有一项时，参考材料可能为空。
② 反思产生 action_reflect 后，代码再次执行的是原来的 actions，不是反思返回的新动作。因此不能说“反思后的新查询已经被执行”。这两点是静态阅读所得，尚未用真实模型完整复现。

第四步：生成并流式返回

final_answer 将当前参考内容和问题拼到 Prompt，调用百炼兼容接口上的 deepseek-r1，使用 stream=True 逐块接收回复并通过 SSE 推给页面。代码也尝试把推理内容与普通答案区分输出。

注意：这里是提示词生成计划 + 程序解析 JSON + 按名称分派函数，不能把它直接说成已使用模型原生 Function Calling，也不能把本目录中另一个 MCP 示例混同为 SalesPilot 的 Agent 实现。

5. 面试需要认识的数据与接口

数据作用与边界
POST /create_session返回 session_id、status、message；当前函数只生成并返回 ID，本身没有写库。
POST /deep_research/?session_id=...请求体包含 {"message":"问题"}；返回 SSE。当前代码没有用 session_id 建立此路径的历史记忆。
规划列表每项含 action_name 和 prompts；拆分后每个动作含 action_name、prompt。
检索记忆列表项类似 {"提问": ..., "结果": ...}，保存这次工具调用的输入与结果。
SSE服务端保持 HTTP 响应，按事件逐步推送内容；页面不必等整段答案生成完才显示。
Embedding项目的 generate_embedding 默认请求 1024 维向量；这只是代码默认参数，并非本次真实调用验证。文本经模型变成数字向量，供检索比较。

6. 为什么这样设计？代价是什么？

选择收益代价或追问
产品文档 + 网页搜索产品资料可结合外部动态和竞品信息。检索到的网页可能过时或错误；需要来源、可信度和时间判断。
模型规划 + 多次工具调用复杂问题可拆分成多个子问题。模型和工具调用增加延迟、费用与失败点；简单问题未必需要复杂流程。
反思设计上可尝试发现证据缺口。需要限制次数并确保执行新动作；当前代码存在动作复用问题。
流式输出用户可更早看到生成内容。流启动后出错时需要给前端明确错误事件，避免页面一直转圈。
JSON 解析 + 字符串分派直观、容易对应代码。输出格式不稳定、工具名拼写不匹配可能失败；可考虑严格 schema 校验及原生工具调用。

额外注意：多个路由中认证被注释、user_id 写死为 1；这是演示代码的限制，不应表述为已实现可靠的多用户隔离。Agent 的检索结果缺失时 Prompt 允许依靠模型自身知识回答，可能产生没有依据的内容。

8. 面试表达：先说清做了什么

30 秒版本

我学习并启动了一个新能源车销售助手项目。它在 RAG 基础上加入 Agent 编排：根据问题规划本地文档检索或网络搜索，再把工具结果交给模型生成回答。我的实践包括启动前后端和数据库，并验证注册、登录和会话创建接口；由于没有可用的模型 API，完整的 Agent 问答还没有跑通。

2 分钟版本

这个项目解决销售人员查询车型资料和组织销售话术的问题。系统前端用 React 和 Vite，后端用 FastAPI；文档检索使用 Elasticsearch，结构化信息使用 PostgreSQL。普通搜索会组合知识库和网络搜索，深度探索则把用户问题交给规划模块，生成工具与查询，再由程序分派到本地检索或网页搜索，尝试反思并流式生成答案。

我实际启动了服务，验证了前端、API、数据库以及注册登录等接口；同时阅读了 Agent 的核心代码。阅读时发现它把首条检索结果从记忆中跳过，而且反思后重新执行原动作，所以这些部分是我识别出的改进点。模型和搜索服务依赖外部 API，我没有验证完整问答，也不会把它说成已上线或已完整跑通。

追问速答

  • Agent 和普通 RAG 有什么不同？RAG 的重点是检索证据并生成；这里 Agent 额外尝试规划多步任务、选择工具和反思，RAG 是其中一种工具。
  • 工具调用怎么实现？本项目深度探索用 Prompt 让模型给出 JSON 计划，再由 Python 按工具名称调用函数，不是已验证的原生 Function Calling。
  • 慢在哪里？规划和反思各需模型调用，工具检索、外部网络以及最终流式生成都可能增加延迟；具体瓶颈需要埋点测量，不能凭代码断言。
  • 怎么提高可靠性？先修正记忆切片与反思动作，给模型输出加 schema 校验、工具超时与重试、迭代次数上限和可观察日志，再用测试集衡量答案与引用质量。
  • 会话记忆在哪里？普通搜索读取历史且在完成分支尝试写库；深度探索中 memory 是本次临时结果，不能直接说具备持久化多轮记忆。
  • 怎么证明理解过代码？指出 agent_plan → adjust_format → process_actions → reflection → final_answer，再说明实际代码中的两处限制。
