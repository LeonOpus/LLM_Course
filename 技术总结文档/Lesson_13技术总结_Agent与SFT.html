Lesson 13：Agent 与 SFT

用旅行助手理解工具调用、多轮轨迹和 LoRA 训练。

先记住：Agent 负责“决定下一步做什么并使用工具”；SFT 负责用示例教模型在上下文中生成合适的回答或工具调用。模型本身不会执行工具，真正执行函数的是应用程序。

2. 项目做什么？

这是一个旅行助手示例，用户可以问旅行攻略、天气、路线或酒店。程序先把工具说明交给模型；如果模型返回工具名称和参数，程序再执行对应函数，把结果交回模型生成回答。主示例是命令行交互，不是现成的网页前端。

例如“推荐北京酒店”：模型决定调用 recommend_hotels，程序执行后再把酒店结果交给模型；在符合代码中的继续条件时，模型可以进一步请求 get_hotel_reviews，最终综合结果回复。工具顺序由提示词、模型输出和程序分支共同决定，不能假设模型永远遵守。

用户提问 → 模型输出工具名和参数 → 程序执行工具
         → 把工具结果放回消息 → 模型继续调用或生成答复

4. 数据怎样变成训练信号？

每条样本是一段对话，常见角色有 system、user、assistant，工具场景中还可能包含工具调用及结果。分词器的聊天模板把消息转换成 token；如果提供工具定义，模板也可以把工具说明放进上下文。

  1. 读取 JSON 数组或 JSONL，找到 messages 或 conversation。
  2. 对完整对话和逐段前缀分别应用聊天模板，用长度差定位 assistant 的区间。
  3. 本次使用 only_last_assistant=True，仅保留最后一个 assistant 区间的标签；其他标签设为 -100，不参与 loss。
  4. 过长时从头部截断，保留尾部；批处理时补齐，补齐位置的标签同样为 -100。

前缀长度差方案依赖聊天模板的前缀结构；换模型或模板后，应检查解码结果和监督区间是否对齐。截断也可能丢掉早期上下文或工具定义。

5. LoRA 在这里做什么？

全量微调会更新基础模型的大量参数；LoRA 在选定的层上增加小型可训练矩阵，基础权重保持冻结。训练时根据最后一条 assistant 的预测误差更新这些矩阵，保存的是增量适配器；加载时仍需要匹配的基础模型。

本次为了快速验证只选择 q_proj,v_proj，r=8；课程脚本默认选择更多投影层、r=32。这两种配置的参数量和训练效果不能直接等同。

三步 loss 分别为 1.1630、3.8902、2.0093；每步样本不同，不能凭这些数字判断收敛或效果提升。

8. 面试时怎么说

30 秒版本

我学习了一个旅行助手：模型根据用户输入选择工具及参数，应用执行工具并把结果交回模型。训练部分把多轮工具调用轨迹转成对话 token，只对最后一轮 assistant 算 loss，通过 LoRA 更新少量参数。我用本机模型做过三步训练和模拟工具链验证，真实接口及最终效果尚未验证。

常见追问

为什么需要工具？模型可以生成调用请求，但无法凭空获得可靠的实时天气、路线或酒店数据；需要程序调用外部服务并回传结果。

为什么把标签设成 -100？让 loss 忽略不希望直接监督的 token，避免把上下文当作当前要学习的输出。

工具调用成功就说明 Agent 好用吗？不够。还要看选得对不对、参数是否合法、多步顺序是否合理、失败时能否处理，以及最终回答是否忠于工具结果。

下一步学习顺序：先读工具调用函数，再读数据标签构造，最后看训练脚本和本次实验，结合独立测试集理解效果评估。
