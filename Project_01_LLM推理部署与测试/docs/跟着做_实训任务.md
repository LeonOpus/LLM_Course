# 跟着项目完成一次推理测试交付

这份练习的目的不是背指标，而是独立完成从接到测试目标、启动服务、验证功能、采集数据到向别人说明结果。Codex 已协助搭好项目和做过一次验证；请逐步自己执行、解释和记录，遇到错误再一起排查。

## 任务背景

假设同事给你一个目标：在单张 RTX 3090 上启动 Qwen2.5-1.5B 的本地推理服务，验证聊天接口，并比较并发 1、2、4 时客户端的延迟和输出吞吐。要求留下可复现的配置、逐请求数据、结论和限制。

这是假设的练习场景，不是客户验收或生产性能保证。不要把本项目结果说成自己此前在客户侧独立完成的优化。

## 第一关：确认环境

1. 看 [项目 README](../README.md) 的环境信息与复现步骤，找到模型路径、服务环境和客户端环境。
2. 检查端口和 GPU 资源是否可用：

```bash
ss -ltn | grep ':18101' || echo '18101 当前没有监听'
nvidia-smi
```

3. 自己回答：这里的 `max-model-len=1024` 是什么限制？`gpu-memory-utilization=0.45` 是配置目标，还是模型真实只占用 45% 显存？如果端口被占用，应先做什么？

记录 GPU、驱动、模型、服务参数、程序版本；不要把访问令牌写进记录。已有记录可参考 [环境清单](../results/20261116_environment.json)。

## 第二关：启动并验证服务

按 README 启动本地服务，等待加载；在另一个终端访问 `/health` 和 `/v1/models`。用 `ss` 确认只监听 `127.0.0.1`。

解释：`/health` 成功能否证明模型能生成？为什么最初这次实验健康检查通过、生成仍然返回 500？参考 [问题排查记录](问题排查记录.md)。

执行 API 与脚本测试：

```bash
/home/leon/miniconda3/envs/llm-course/bin/python -m pytest tests -q
```

记录通过、失败数量。测试失败时保存错误类型和复现步骤，不跳过失败直接写“项目跑通”。

## 第三关：运行小样本压测

按 README 各跑一组 `--concurrency 1`、`2`、`4`，每组先用 `--requests 6 --warmup 1 --output-tokens 16` 做冒烟。每次使用不同的 `--output-dir`，不要覆盖原记录。

查看 `summary.json` 和 `requests.jsonl`：

- 成功和失败各多少？`output_tokens` 真的是 16 吗？
- TTFT、TPOT、E2E、输出 token 吞吐各自的单位和分母是什么？
- 如果某个请求没有 usage 或没有 `[DONE]`，它会被记为成功吗？
- GPU 采样看到的是整卡指标还是这个进程的专属指标？

冒烟仅用于检查流程，样本很少，不用于评价 P95。确认流程后再按 [测试方案](测试方案.md) 运行正式组。

## 第四关：分析与交付

打开 [本次测试报告](测试报告.md)，挑并发 1 和 4 各一轮，说出两组请求数、TTFT、TPOT、吞吐；解释它们的变化，并说明本实验不能证实什么。

然后自己写一页报告：**目标与环境 → 方法与样本 → 原始结果 → 观察 → 限制 → 下一步验证**。如果发现结果不同，先核对环境、模型和负载，不要挑选好看的数字。

## 第五关：停止服务

在服务所在终端按 Ctrl+C，检查 `ss -ltn | grep ':18101'` 无结果。服务可能需要几秒退出；没有确认退出前，不要声称端口已经释放。

练习完成后，你应能用 3 分钟讲清一次测试从目标、执行到结果交付的全过程；更深的性能原因需要单独设计对照与 profiling，不能只凭指标猜结论。
