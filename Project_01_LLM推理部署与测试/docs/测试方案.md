# 推理服务测试方案

## 1. 测什么

验证本机单卡部署是否能正常启动、返回模型列表和生成结果；检查流式输出以及错误输入响应；观察在固定请求内容和输出上限下，并发从 1 增至 2、4 时客户端看到的性能变化。**不评判模型业务准确率，也不做真实线上容量承诺。**

## 2. 实验条件

- 以 `results/20261116_environment.json` 中的硬件、模型 SHA256、软件版本和服务参数为准。
- 本地模型通过回环地址 `127.0.0.1:18101` 提供 OpenAI 风格聊天接口；客户端 `httpx` 使用 `trust_env=False`，不走环境代理。
- 输入是 6 条固定的短中文问题，依序循环。每次 24 个请求，最多生成 48 个 token，temperature=0；每组先完成 2 个串行预热请求。各并发组重复 3 次，按 1→2→4 顺序循环。
- 程序一次创建 24 个任务，由信号量限制同时进行的 HTTP 请求数，前一个结束后才补下一个；这属于**闭环固定并发测试**，不是固定到达速率测试。请求之间共用一个异步 HTTP 连接池。
- 每个请求的耗时从获得信号量并准备发送请求后开始，结束于客户端接收 `[DONE]`；等待信号量的 `client_queue_ms` 单独记录，不包含在单次 E2E/TTFT 中。整组吞吐的时间窗口包含整组任务执行与等待。
- 服务端自动前缀缓存配置为关闭。模型可能提前输出结束符；实际输入和输出 token 数由流式结束时服务端返回的 `usage` 记录。最大输出 48 不等于每个请求一定输出 48。

## 3. 功能测试

| 用例 | 预期 |
|---|---|
| GET /health | 200 |
| GET /v1/models | 存在 `qwen-local` |
| 非流式生成 | 200，存在文本和有效的输出 token 数 |
| 流式生成 | 有非空文本、usage 和 `[DONE]` |
| 不存在的模型 | 404 |
| max_tokens 为负 | 400 或 422 |

另用模拟 HTTP 流测试百分位计算、正常 usage、usage 缺失时按失败处理。

## 4. 指标口径

- **TTFT（客户端近似）**：从请求开始到收到第一个非空文本 SSE 块。一个块可能包含多个 token，也可能前面出现空块；因此这里是“首个可见文本块延迟”，不保证等同引擎内部首 token 产生时间。
- **E2E**：从请求开始到客户端收到 `[DONE]`。包含网络/服务及流结束信号处理；不含信号量外等待。
- **TPOT（客户端近似）**：`(E2E - TTFT) / (completion_tokens - 1)`；token 数来自服务端 usage。只在输出 token 数大于 1 时计算。因为首个非空文本块可能含多个 token，且 E2E 包含结束信号，不能把它视为每个 token 都精确测时；它也不是逐 token 的 ITL。
- **成功请求吞吐**：成功请求数 / 整组墙钟时间，单位请求/秒。
- **输出 token 吞吐**：成功请求的 `completion_tokens` 总数 / 整组墙钟时间，单位 token/秒，属于服务总吞吐，不是单个请求生成速度。
- **P50/P95**：对每组成功请求的单请求数值排序，使用位置 `(n-1)×p` 的线性插值。每组只有 24 个请求，P95 样本偏少；只作演示，不代表稳定长尾指标。
- `gpu.csv` 每约 0.5 秒采样一次 `nvidia-smi` 显存和 GPU 利用率；包含预热及测试阶段，采样可能错过瞬时峰值，也无法单凭利用率判断瓶颈。

## 5. 失败处理与比较原则

非 200、无结束标记、无文本、没有服务端 usage、网络超时等均记录为失败；不能把失败请求当成 0 ms 的成功请求。正式报告同时展示成功/失败数。比较时固定模型、精度、服务参数、请求数和问题集合；先看三轮结果波动，再解释并发变化。结果受同机负载影响，任何推断都需额外对照或 profiling 确认。
