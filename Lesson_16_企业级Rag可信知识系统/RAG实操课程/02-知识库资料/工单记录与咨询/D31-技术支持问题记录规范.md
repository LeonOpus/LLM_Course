# 技术支持问题记录规范

本资料中的设备、参数、规则和案例均为课程虚构，不可用于真实设备操作。

本规范用于把用户的一段自然语言整理成可以交接的问题记录。目标是保留设备、日期、现象和证据之间的关系，而不是通过补写字段把不确定内容变成事实。

## 一 一条问题记录应该保留什么

| 字段 | 含义 | 缺失时怎样记录 |
| --- | --- | --- |
| model | 完整型号 | null，并列入待补充 |
| serial_number | 本台设备的序列号 | null，不能用型号代替 |
| order_date | 订单日期，用于选择政策 | null，不能复制签收日期 |
| receipt_date | 签收日期，用于保修起算 | null，不能复制订单日期 |
| symptom | 用户观察到的现象 | 保留原话，单独标注待核实推断 |
| alarm_code | 告警代码 | null，不能把缺失改成无告警 |
| attachments | 购买凭证、现场照片及可选日志 | 逐项记录有无 |

## 二 型号和日期分别核对

型号描述设备类型，序列号识别具体设备，两个字段不能互换。购买凭证中的订单日期用于选政策版本，签收日期用于确定保修起点；用户今年咨询，不表示订单也在今年。

记录人员可以整理格式，例如将明确的“2025年12月20日”记成“2025-12-20”；用户没有给出日期时，不得自行填入当天日期。日期字段无法确认时保持null，向用户提问。

## 三 附件存在不等于结论成立

RMA必填材料包括型号、序列号、购买凭证、故障现象、告警代码和现场照片；运行日志为选填。材料不齐时先补充，不声称已经批准保修。

- 购买凭证：记录文件名及核查状态。
- 现场照片：记录文件名及对应现象。
- 运行日志：已有时附上，缺失不改写为必填。
- 尚未获得的材料：留空并加入待补充清单。

## 四 JSON记录样例

下面是WO-001的教学整理样例。工单已有的日期、告警和原因按原文保留；序列号、附件文件名并未出现在该工单中，所以保持null或空列表。空列表表示本条记录未登记附件，不足以证明用户从未提交附件。

```json
{
  "case_id": "WO-001",
  "model": "X200",
  "serial_number": null,
  "order_date": "2025-12-20",
  "receipt_date": "2026-01-03",
  "registered_date": "2026-01-10",
  "region": "中国大陆",
  "symptom": null,
  "alarm_code": "E101",
  "known_cause": "滤芯自然磨损",
  "attachments": [],
  "record_note": "仅整理课程工单已有字段，不自动形成保修批准结论"
}
```

在JSON中，字典用花括号包住字段；字符串加双引号；null表示当前没有一个已知值；[]是空列表。把null改成字符串"null"会改变数据类型。以上是记录格式说明，不是新售后政策。

## 五 交接之前复核

按“原话—结构化字段—附件—缺项—结论”顺序检查。若只有告警而没有原因依据，不填已确认原因；若只知道订单日期，不计算缺少签收起点的保修日期。附件补齐以后仍需按原因和适用条款判断。
