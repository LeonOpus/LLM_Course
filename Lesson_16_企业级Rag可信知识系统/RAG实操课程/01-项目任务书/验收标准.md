# 验收标准

验收分两层：**做完了没有**（12 条功能验收）和 **做得好不好**（用验收题集量出来的 7 个指标）。两层都过，才算交付。

## 一、12 条功能验收

每一条都是"给定什么、做什么、应看到什么"，能被一个测试、一次浏览器操作或一次评估运行检查。开发时按这个顺序逐条实现，每条通过后再做下一条。

| 编号 | 给定 | 当 | 应看到 | 怎么查 |
|---|---|---|---|---|
| AC-01 | 后端启动 | 请求 `GET /api/health` | HTTP 200，`status: ok`；只说明进程在，不说明云服务可用 | 接口测试 |
| AC-02 | 前端启动，后端在或不在 | 打开页面 | 后端在时显示"已连接"；后端停了显示"请求失败"，不显示假状态 | 浏览器 |
| AC-03 | 知识库页 | 上传空文件、不支持的类型、正常文件 | 前两者明确报错；正常文件状态为"已上传"，不是"已解析" | 接口测试 |
| AC-04 | 一份 PDF、一份 Office | 提交 DocMind 解析 | 异步：先"解析中"，完成后"已解析"，原始结果落盘；任务失败不标"已解析" | 真实调用 + 固定失败样例 |
| AC-05 | 九种格式各一份 | 解析并查看块 | 每块有该格式合适的定位；Word 无页码就不给页码；不编造 | 本地确定性测试 |
| AC-06 | 已解析文档 | 切块、向量化、入库 | 每段带来源；向量 1024 维写入 Milvus；检索能返回真实候选；重启 Milvus 后还在 | 本地测试 + 真实服务 |
| AC-07 | 知识库为空 / 问资料外的事 / 缺条件 | 提问 | 分别：拒答；拒答；反问缺什么。引用只能指向本次上下文里的片段 | 接口测试 + 题目评估 |
| AC-08 | 一次问答 | 展开检索过程 | 看到候选、（重排）、最终上下文、参数、耗时；停止接收后迟到内容不显示 | 浏览器 |
| AC-09 | 验收题集 | 校验文件 | 140 题字段齐全、题型配额对、冒烟 20 题是其子集、证据编号能对到原件 | 文件核验 |
| AC-10 | 固定配置 | 跑 20 题冒烟、再跑 140 题 | 每次运行有独立目录，记录配置、语料指纹、逐题记录；报告可追溯，不能手改数字 | 实际评估运行 |
| AC-11 | 基线 + 一个改动 | 同题对照 | 能切换单项策略；报告同时列出改善题、退步题、不变题，各自能追到证据 | 开发集回归 |
| AC-12 | 冻结的最终配置 | 验收方跑 60 道保留题 | 报告给出指标、题量、耗时和验证范围；开发方不能提前拿到保留题 | 封存评估 |

## 二、7 个质量指标

全部在验收题集上算。每个指标必须同时给出 **分子 / 分母**，百分比单独出现无效。

| 指标 | 一题算"通过"的条件 | 分母 |
|---|---|---|
| 回答正确率 | 参考答案里 `required` 的要点全部覆盖，没有出现 `critical_errors`，数值题的数值和单位在容差内 | 已复核的题 |
| 行为正确率 | 实际行为和 `expected_behavior` 一致：该答的答了，该算的列了算式，该拒的拒了，该问的问了 | 已复核的题 |
| 候选证据组召回 | `evidence_groups` 里每一组至少有一个等价证据出现在检索候选里；按题算比例后宏平均 | 有证据组的题 |
| 上下文证据组召回 | 同上，但看的是最终交给模型的上下文，不是候选 | 有证据组的题 |
| 引用支持率 | 回答里每个引用，对应片段真的支持它所标注的那句话 | 有引用的题 |
| 引用完整率 | 回答里每个需要出处的结论都标了引用 | 已复核的题 |
| **完整 RAG 成功率** | 回答正确 **且** 引用全部支持 **且** 引用完整。拒答题和澄清题没有正例证据，行为和内容复核通过即可 | 已复核的题 |

三个容易混的地方：

1. **答对不等于引用对。** 回答 180 W，引用的却是另一个型号的参数行，答案正确率算过，引用支持率不算过。
2. **候选里有，上下文里没有，是两个不同的问题。** 前者是检索问题，后者是上下文选择问题（被预算挤出去了）。优化前先看是哪一层丢的。
3. **"待复核"不是 0 分。** 复核结果只有 true / false / null 三种，null 表示还没判断。报告里的百分比只描述已复核的子集。

## 三、评分怎么做

- 程序能查的先程序查：引用编号存不存在、摘录是不是原文、来源版本对不对。
- 语义要人判断：一句话是否被证据支持、要点是否覆盖。可以用百炼模型辅助初判，但关键数值、单位和代表性失败题必须人工复核，报告要标明哪些是模型辅助、哪些是人工。
- 参考答案只给评分程序看，问答系统只收问题和对话历史。

## 四、优化实验的规矩

1. **先冻结基线。** 固定题集、语料、切块、模型、参数，跑一次，存下来。之后所有对比都和它比。
2. **一次只改一处。** 改了表格切块就不要同时改检索参数；否则说不清是谁起了作用。
3. **同题同预算。** 对照组和基线用同一批题、同样的上下文预算。
4. **改善和退步都要报。** 一个改动让 5 题变好、3 题变坏，就写 +5 / −3，并解释那 3 题为什么坏。
5. **没提升也是结果。** 试了没用的改动照样记录，写清楚为什么没用，然后撤回。
6. **保留题只跑一次。** 60 道保留题在最终配置冻结后由验收方跑；不能拿它调参。

## 五、交付清单

- 能在一台 macOS 或 Windows 11 开发机上启动的前后端，附启动说明。
- 规格文档：功能范围、接口表、12 条验收的实现状态。
- 36 份原件全部入库后的知识库。
- 基线报告（20 题冒烟 + 140 题开发集）和至少两次优化对照报告，每次都有改善、退步、不变三张清单。
- 冻结的最终配置说明，交给验收方跑保留题。
